# 한글 프로그램의 실제 동작

에디터 개발 참고용. 파일 형식(바이트 배치)은 `hwp-format.md`, 명세 오류는 `hwp-5.0-errata.md`에 있다. 여기에는 **한글이 무엇을 저장하고, 어떻게 읽고 그리는지** 관찰한 것만 적는다.

- 환경: macOS용 한컴오피스 한글 12.30.0(6544). Windows 동작으로 일반화하지 않는다.
- 각 항목 끝의 괄호는 근거다. 실험 파일은 `experiments/`에 있다.

## 새 문서의 기본값

- 빈 문서를 저장하면 BorderFill이 두 개 생긴다. 둘 다 네 방향 선 없음이다. 첫째는 채우기 없음, 둘째는 단색 채우기(배경 `FFFFFFFF`, 무늬색 `#999999`, 무늬 없음)다. (TIL 2026-10-29, 샘플 바이트)
- 대각선은 그리지 않아도 선 정보가 기본값으로 들어 있다: 실선(1), 0.1mm, 검정. 대각선을 그릴지는 속성 비트(`slashShape` 등)가 정한다. (TIL 2026-10-30)

## 셀 배경 채우기

- **UI는 하나만 고른다**: 채우기 없음, 색, 그러데이션, 그림 중 하나. 셀 채우기에 투명도 설정은 없다.
- **저장도 하나만 한다**: 다른 종류로 바꿔 저장하면 이전 종류의 블록이 지워진다. 그림에서 다른 종류로 바꾸면 `BinData`의 그림까지 지워진다. (실측 저장 파일)
- **편집 중에는 이전 값을 기억한다**: 그림 → 그러데이션 → 그림으로 바꾸면, 문서를 닫기 전까지는 이전 그림이 돌아온다. 파일에는 남지 않으므로 다시 열면 없다.
- **여러 종류가 켜진 파일도 연다**: 오류 없이 열고, **이미지 > 그러데이션 > 색** 순으로 하나만 쓴다. 본문에 그려진 모습과 속성 창 중 어느 쪽에서 본 결과인지는 구분해 기록하지 않았다. 종류 5는 속성 창에서도 그러데이션이었다. (`experiments/fill-multi-kind-priority`)
- **번짐 정도 0인 그러데이션은 그리지 않는다**: 속성 창 값은 정상으로 보인다. 50, 255는 그린다. 명세 범위(0–100)와 달리 255도 쓴다. (`experiments/fill-gradient-step-zero`)
- **macOS 한글은 그러데이션 색을 2개까지만 설정**할 수 있다. 3색 이상은 Windows에서 확인해야 한다.
- **채우기 끝의 알 수 없는 1바이트**는 0, 50, 128, 255로 바꿔도 표시가 같다. 한글은 이 값을 쓰지 않는 것으로 보인다. 저장할 때는 0을 쓴다. (`experiments/fill-trailing-unknown-byte`)

## 색 없음과 흰색

셀 배경의 `FF FF FF FF`는 "색 없음"이고, `FF FF FF 00`은 흰색이다. 최상위 바이트의 의미와 다른 필드의 동작은 확인하지 않았다. (`experiments/colorref-high-byte`)

## 그림 채우기

- 채우기 방식 값 15는 UI에서 "원래 크기에 비례하여"로 표시된다.
- 그림 효과 드롭다운에 값 3(8×8 패턴)은 보이지 않는다.
- 그림 정보는 명암이 밝기보다 먼저 저장된다(명세와 반대).

## 문단 번호 모양

- 번호 모양 드롭다운에는 17개(값 0–16)가 있다. 명세 표 41은 0–14만 적고 15(갑, 을, 병)와 16(甲, 乙, 丙)이 빠져 있지만, 각주/미주 모양의 표 134에는 0–16이 모두 있다.
- **범위 밖의 값(17–31)은 본문에서 값 0(1, 2, 3)으로 그린다**. 문단 번호 설정 창의 번호 모양 드롭다운에서는 아무 항목도 선택되지 않은 상태로 보인다. 파일은 오류 없이 연다. (`experiments/numbering-format-bits`, 2026-11-11)
- **번호 모양 위쪽 비트 실험**: 모든 수준을 甲, 乙, 丙(16, 비트 5–9)으로 두고 그 위 비트를 수준마다 하나씩 켰다. 결과는 파일 단위로 관찰한 것이다. (`experiments/numbering-format-high-bits`, 2026-11-12)

  | 파일 | 1–7수준에 켠 비트 | 설정 창 드롭다운 | 본문 |
  |---|---|---|---|
  | `bit-10` | 10 (1수준만) | 빈칸 | 1, 2, 3 |
  | `width-11-17` | 11–17 | 빈칸 | 1, 2, 3 |
  | `width-18-24` | 18–24 | 甲, 乙, 丙 | 1, 2, 3 |
  | `width-25-31` | 25–31 | 甲, 乙, 丙 | 甲, 乙, 丙 |

  의심되나 확인되지 않음: 한글은 범위 밖 값을 만나면 기본값 0으로 처리하는 것 같다. 본문은 0(1, 2, 3)으로 그리고, 드롭다운은 아무것도 선택하지 않는다. 정렬 값 3도 같은 모양이다. 설정 창과 본문이 어느 비트까지를 번호 모양 값으로 읽는지는 확정하지 못했다.

  js-hwp는 비트 5–9만 읽고 쓴다. 한글 UI에서 고를 수 있는 값이 0–16뿐이라 한글이 저장한 파일은 이 범위를 벗어나지 않는다.
- **정렬 값 3(명세는 0–2만 정의)은 본문에서 왼쪽으로 그리고**, 설정 창의 정렬 드롭다운은 빈칸이다. (`experiments/numbering-align-out-of-range`)
- **본문과의 간격**: 속성 비트 4가 0이면 값은 %, 1이면 HWPUNIT이다. 설정 창에서 길이 단위를 고르면 비트 4가 켜진다. 고른 단위는 저장되지 않아서 다시 열면 pt로 보인다(10 mm로 설정 → 2834 → 다시 열면 28.3 pt). 비트 4만 켠 값 70은 0.7 pt로 보인다. **너비 조정**도 HWPUNIT이고, 단위가 저장되지 않는 것도 같다. (`experiments/numbering-distance-kind`)

## 문단 모양

- **줄 간격을 바꾸면 두 줄 간격 필드를 함께 쓴다**: 문단 모양 레코드에는 5.0.2.5 미만용과 5.0.2.5 이상용 줄 간격 필드가 따로 있다. 줄 간격을 160%에서 180%로 바꾸자 오프셋 24와 50의 값이 둘 다 `A0`(160)에서 `B4`(180)로 바뀌었다. Windows용 한컴오피스 한글 13.0.0.4225에서 관찰했다(이 문서의 기본 환경인 macOS가 아님). 백분율이 아닌 줄 간격 종류는 확인하지 않았다. (TIL 2026-11-14, hwp-watch)
- **여백과 문단 간격은 HWPUNIT의 2배로 저장한다**: 왼쪽·오른쪽 여백, 첫 줄 들여쓰기/내어쓰기, 문단 간격 위·아래 모두 같다. 25pt → 5000, -10pt → -2000. 첫 줄은 들여쓰기 10pt → 2000, 내어쓰기 10pt → -2000으로 부호로 구분한다. UI는 0.1pt(저장 값 20) 미만을 받지 않는다. Windows용 한글의 입력 범위는 왼쪽·오른쪽 여백 -415.0~415.0pt, 문단 간격 위·아래 0~841.8pt다. (`hwp-5.0-errata.md` E18)
- **문단 테두리 간격은 HWPUNIT 그대로 저장한다**: 테두리 탭의 왼쪽·오른쪽·위쪽·아래쪽 간격. 1pt → 100. Windows용 한글은 0~25mm, 0~70.8pt만 받는다. (`hwp-5.0-errata.md` E18)
