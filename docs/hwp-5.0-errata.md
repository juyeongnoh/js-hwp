## 2026-10-28 실험 기록

이 절은 실제 바이트 검사, 한글 화면에서의 관찰, 미확인 사항을 구분한다. 명세와 다른 표시가 나왔다는 이유만으로 명세의 모든 설명이 잘못됐다고 단정하지 않는다.

- 에이전트가 직접 화면을 확인한 환경: macOS 한글 `12.30.0`, 빌드 `6313`, 읽기 전용 모드.
- 대각선의 개별 조합은 사용자가 실제 한글에서 연 뒤 제공한 캡처로 확인했다. 그 캡처의 앱 버전은 별도로 확인하지 않았다.
- Windows 한글에서의 비교는 별도 후속 작업이다. 아래 macOS 관찰을 Windows의 동작으로 일반화하지 않는다.
- 이 기록에서 HWPX는 HWP 동작을 확정하는 기준으로 사용하지 않는다.

| sample4.hwp |                   36 |
| 합계        |                  630 |

검사한 레코드는 모두 아래 32바이트 구간을 포함했다. 나머지 바이트에는 채우기 정보 등이 이어진다. 오프셋은 레코드 헤더를 제외한 페이로드 시작 기준이다.

| 오프셋 | 내용                                |
| ------ | ----------------------------------- |
| 0~1    | 속성 UINT16                         |
| 2~7    | 왼쪽: 종류 1B + 굵기 1B + 색상 4B   |
| 8~13   | 오른쪽: 같은 6B 구성                |
| 14~19  | 위쪽: 같은 6B 구성                  |
| 20~25  | 아래쪽: 같은 6B 구성                |
| 26~31  | 대각선: 종류 1B + 굵기 1B + 색상 4B |

예를 들어 sample3.hwp의 한 레코드는 다음처럼 읽힌다.

```text
00 00                 속성
00 00 FF FF FF FF     왼쪽
00 00 FF FF FF FF     오른쪽
01 00 5B 9B D5 00     위쪽
01 00 5B 9B D5 00     아래쪽
00 00 FF FF FF FF     대각선
```

일반 테두리 네 방향과 대각선은 바이트 길이와 종류 값의 타입이 같다. 대각선도 `BorderLine`(종류는 `LineStyle`)으로 모델링한다. 명세 표 27의 `0=Slash`, `1=BackSlash`, `2=CrookedSlash` 해석은 E6에서 실제 값과 맞지 않는 것을 확인했다.

현재 읽기 구현은 네 방향을 종류·굵기·색상 한 세트씩 읽고, 대각선은 `hasMore(6)`일 때 읽는다. 이는 현재 파서의 처리 정책이며, 잘린 대각선 레코드가 정상이라는 실험 결과는 아니다.

### E2. 일반 테두리선 종류 값

정상적으로 열리는 sample.hwp를 기준으로, 네 방향 선 종류를 0~17로 바꾼 사본 18개를 실제 한글에서 열었다. 굵기와 색상은 동일하게 고정했다. 각 사본의 종류 바이트가 의도한 값인지와 DocInfo 이외의 원본 스트림 보존을 확인했다.

| 실제 값 | 관찰한 표시 또는 추정 이름      | 판정                                                 |
| ------: | ------------------------------- | ---------------------------------------------------- |
|       0 | 선 없음                         | 화면 확인                                            |
|       1 | 실선                            | 화면 확인                                            |
|       2 | 긴 점선                         | 화면 확인                                            |
|       3 | 점선                            | 화면 확인                                            |
|       4 | 일점쇄선                        | 화면 확인                                            |
|       5 | 이점쇄선                        | 화면 확인                                            |
|       6 | 더 긴 선분의 반복               | 화면 확인                                            |
|       7 | 원형 점의 반복                  | 화면 확인                                            |
|       8 | 이중선                          | 화면 확인                                            |
|       9 | 가는선 + 굵은선 이중선          | 화면 확인                                            |
|      10 | 굵은선 + 가는선 이중선          | 화면 확인                                            |
|      11 | 가는선 + 굵은선 + 가는선 삼중선 | 화면 확인                                            |
|      12 | 물결                            | 화면 확인                                            |
|      13 | 물결 이중선                     | 화면 확인                                            |
|      14 | 두꺼운 3D                       | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
|      15 | 두꺼운 3D, 광원 반대            | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
|      16 | 3D 단선                         | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
|      17 | 3D 단선, 광원 반대              | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |

14~17은 속성 bit 0의 3D 효과를 켠 사본 4개도 비교했지만 선이 표시되지 않았다. 이 결과만으로 값이 무효이거나 의미가 없다고 결론 내리지 않는다. 추가 속성이나 한글 버전·플랫폼에 따른 표시 조건은 미확인이다.

명세의 실선 이후 항목이 실제 값보다 1 작게 적힌 것은 `선 없음=0` 항목 누락에 따른 차이로 추정한다. 0~13은 관찰로 뒷받침되지만, 3D 계열 전체의 대응까지 시각적으로 확정한 것은 아니다.

시험 중 DocumentBuilder로 새로 생성한 별도 문서는 한글에서 파일 손상 경고가 나왔다. 그 문서는 위 결과에서 제외하고 정상 원본의 바이너리를 직접 변경한 사본으로 검증했다. 생성 문서의 손상 원인은 이번 실험 범위에서 조사하지 않았다.

### E3. bit 8과 bit 9의 독립적인 꺾임 플래그

대각선 샘플 HWP의 첫 행 첫 번째 셀을 대상으로, Slash 모양과 BackSlash 모양을 모두 `010`으로 고정했다. bit 10과 나머지 속성은 고정한 채 bit 8~9만 바꾼 네 파일을 사용자가 실제 한글에서 비교했다.

| 파일              | 속성 UINT16 | bit 9 | bit 8 | 첫 번째 셀에서 관찰한 동작 |
| ----------------- | ----------- | ----: | ----: | -------------------------- |
| s010-b010-c00.hwp | 0x0048      |     0 |     0 | 둘 다 직선                 |
| s010-b010-c01.hwp | 0x0148      |     0 |     1 | Slash(`/`)만 꺾임          |
| s010-b010-c10.hwp | 0x0248      |     1 |     0 | BackSlash(`\`)만 꺾임      |
| s010-b010-c11.hwp | 0x0348      |     1 |     1 | 두 대각선 모두 꺾임        |

따라서 bit 8~9의 합성값 0/1/2/3은 이 조건에서 두 방향 꺾임 플래그의 조합이다. `3`이 미확인이라는 이전 중간 판단은 이 네 장의 캡처로 갱신한다. 두 비트를 하나의 boolean으로 줄이면 어느 방향이 꺾였는지 손실된다.

현재 모델은 다음처럼 분리한다.

```ts
slashCrooked: bit(properties, 8),
backSlashCrooked: bit(properties, 9),
backSlashCrookedSpec: bit(properties, 10),
```

bit 10은 명세에서 BackSlash 꺾은선으로 정의하므로 `backSlashCrookedSpec`으로 독립적으로 읽고 쓴다. bit 9와 OR로 합치거나, bit 9의 값을 bit 10에도 복제하지 않는다. **bit 10을 켰을 때의 실제 효과는 아직 확인하지 않았다.**

이 실험은 두 모양이 모두 `010`이고 중심선 bit 13이 꺼진 조건의 결과다. 중심선이 켜진 조합 등 다른 조건에서도 두 비트의 역할이 항상 같다고 일반화하지 않는다.

### E4. 대각선 모양 코드의 화면 관찰

아래 값은 파일 이름과 사용자가 제공한 캡처를 기준으로 한다. 대상은 항상 첫 행 첫 번째 셀이며 나머지 셀은 원본 그대로다.

| 파일 또는 조건    | 관찰 결과                    | 해석 범위                                                                                |
| ----------------- | ---------------------------- | ---------------------------------------------------------------------------------------- |
| s001-b000-c00.hwp | 대각선 표시 없음             | `001=1`은 명세에 의미가 열거되어 있지 않다. 이 조건에서 표시되지 않은 것을 확인했다.     |
| s011-b000-c00.hwp | `/` 직선 표시                | 명세의 `011: LeftTop → BottomEdge` 설명과 세부 모양이 직접 대응하지 않는다.              |
| s110-b000-c00.hwp | `/` 직선 표시                | `110=6`이 원본 샘플에 없다는 중간 한계를 갱신한다. 직접 설정한 사본에서 표시를 확인했다. |
| s010-b010-c00.hwp | `/`와 `\`가 교차하는 두 직선 | 두 모양 `010`이 함께 켜진 조건이다.                                                      |

`011`과 `110`은 모두 가운데 비트 `010`이 켜져 있다. 현재 환경이 가운데 비트만으로 기본 대각선을 그리고 나머지 비트의 세부 모양을 표시하지 않는다는 설명은 **가설**이다. 명세의 오류인지, 플랫폼 차이인지, 추가 조건이 필요한지는 확정하지 못했다.

표시가 같더라도 서로 다른 코드 2/3/6/7을 같은 값으로 정규화하지 않는다. 원시 3비트 값을 보존하며, 명세에 기재된 모양 설명과 실제 화면 관찰을 구분한다. 나머지 값·방향·회전 조합까지 전수 시각 검증한 것은 아니다.

### E5. 256개 조합 파일의 생성과 검증 범위

[대각선 샘플 HWP 원본](https://github.com/edwardkim/rhwp/blob/main/samples/%EB%8C%80%EA%B0%81%EC%84%A0%EC%83%98%ED%94%8C.hwp)을 복사해 다음 세 필드의 전체 비트 범위를 조합했다.

- Slash bit 2~4: 0~7.
- BackSlash bit 5~7: 0~7.
- 꺾임 bit 8~9: 0~3.
- 합계: `8 × 8 × 4 = 256`개.

원본 HWP 자체에서 다음을 확인했다.

- BodyText/Section0의 첫 번째 셀 LIST_HEADER는 `row=0`, `col=0`, BorderFill 참조 번호 `4`다.
- 대상은 DocInfo에서 네 번째로 등장하는 BorderFill이다. HWP BorderFill 페이로드에 별도 ID 필드가 있는 것이 아니다.
- 대상 레코드 헤더는 압축 해제된 DocInfo의 오프셋 994, 속성은 998~999에 있다.
- TABLE의 두 cellzone은 대상 셀에 겹치지 않는다.

각 파일에서 그 속성 2바이트 안의 bit 2~9만 변경했다. 256개를 다시 읽어 지정값, 레코드 경계, 다른 속성 비트, 나머지 8개 원본 스트림의 SHA-256 보존을 검사했다. 당시 파서에서 세 필드의 추출값도 256/256개가 일치했다. 이후 모델을 bit 8/9/10 각각의 boolean으로 분리하고, 여덟 조합의 읽기·쓰기 보존 테스트를 추가했다.

파일은 Slash·BackSlash가 모두 명세에 열거된 값 `0/2/3/6/7`인 100개와, 둘 중 하나라도 미정의 값 `1/4/5`인 156개로 나눴다. 이 분류는 모양 두 필드에 관한 것이며, 모든 조합의 시각적 의미가 명세에 정의됐다는 뜻은 아니다.

**256개 전체의 한글 화면 검증은 완료하지 않았다.** 화면 도구가 이미지 생성 오류, 이후 커널 파일 오류로 실행되지 않았다. E3·E4는 이후 사용자가 직접 열어 제공한 개별 캡처로 확인한 범위다. 바이너리 검사가 통과한 것을 한글의 표시 동작 검증으로 취급하지 않는다.

시험 파일의 내장 미리보기는 원본을 보존했다. 따라서 Finder 미리보기나 썸네일은 변경 후 결과가 아니며, 한글에서 본문을 직접 연 화면을 사용해야 한다.

### E6. 대각선 종류 바이트의 실제 의미 (2026-10-30)

사용자가 macOS 한글 12.30.0(6544)에서 직접 만든 파일을 프로젝트 파서로 읽어 확인했다.

| 조건                            | 대각선 6B (종류, 굵기, 색) | 비고                                                                        |
| ------------------------------- | -------------------------- | --------------------------------------------------------------------------- |
| 빈 문서                         | `1, 0, #000000`            | 대각선 모양 비트 `slashShape`·`backSlashShape`는 모두 0이다.                |
| 1×1 표, 네 방향 빨간색 1mm 실선 | `1, 0, #000000`            | 네 방향은 `1, 10, #BD3D3D`(실선, 1.0mm)로 읽혔다. 대각선은 지정하지 않았다. |
| 대각선 선 종류를 점선으로 지정  | 종류 `3`                   | `LineStyle.Dotted = 3`과 일치한다.                                          |

대각선이 없는 파일에서도 종류가 `1`이므로, 표 27대로라면 대각선 없이 `BackSlash`가 기록된 셈이 된다. 반면 표 25 계열로 읽으면 `1=실선`, `3=점선`으로 두 관찰이 모두 설명된다. 프로젝트의 HWPX 픽스처 두 개도 대각선이 없는 BorderFill에 `<hh:diagonal type="SOLID" width="0.1 mm" color="#000000"/>`를 기록한다(HWP 동작의 확정 근거로는 쓰지 않는다). E1의 sample3.hwp 레코드처럼 종류 `0`이 기록된 경우는 `0=선 없음`으로 읽힌다.

이에 따라 HWP 라이터는 대각선 정보가 없을 때 한글 빈 문서와 같은 `1, 0, #000000`을 기록한다. 종류 `0`과 `2` 이상 중 `3`을 제외한 값은 한글에서 개별 설정해 비교하지 않았다.

## 2026-10-30 실험 기록: 채우기 정보 (표 28)

환경은 macOS용 한컴오피스 한글 12.30.0(6544)이다. 실험 파일, 기반 파일, 재현 명령은 `experiments/`의 각 폴더에 있다. 여기에는 결론과 판단 범위만 적는다.

### E7. 그러데이션 필드 크기 (`experiments/fill-gradient-field-sizes`)

같은 그러데이션 값을 명세의 `INT16 × 6` 배치와 `UINT8 + INT32 × 5` 배치로 넣었다. 뒤 배치는 속성 창에 값이 그대로 보였고, 명세 배치는 엉뚱한 값(시작·끝 색 검정, 중심 100/0, 기울임 359)으로 읽혔다. 이후 한글에서 그러데이션을 직접 지정해 저장한 레코드도 뒤 배치였다.

색 수가 2보다 클 때의 위치 배열은 확인하지 못했다. macOS 한글은 그러데이션 색을 2개까지만 설정할 수 있다.

### E8. 번짐 정도 (`experiments/fill-gradient-step-zero`)

번짐 정도만 `0`, `50`, `255`로 바꿨다. `0`은 속성 창 값이 정상인데 셀이 칠해지지 않았고, `50`과 `255`는 칠해졌다. 한글이 저장한 그러데이션에도 `255`가 있었으므로 명세의 `0 -100` 범위는 실제와 다르다.

### E9. 채우기 정보의 꼬리와 그림 정보

한글이 직접 저장한 레코드의 채우기 부분이다.

```text
채우기 없음  00 00 00 00 | 00 00 00 00
단색         01 00 00 00 | (단색 12B)            | 00 00 00 00 | 00
이미지       02 00 00 00 | 0f 4b 32 00 01 00     | 00 00 00 00 | 00
그러데이션   04 00 00 00 | (그러데이션 29B)      | 01 00 00 00 | 32 | 00
```

- 추가 채우기 속성 길이 `DWORD`는 모든 경우에 하나만 있다. 그러데이션일 때만 `1`이고 번짐 중심 1B가 따라온다. 명세의 네 행은 이 두 필드를 두 번 적은 것이다(정정 8, 9).
- 채우기가 있으면 마지막에 1B가 더 있고, 모두 `00`이었다(정정 10).
- 이미지 행은 유형 `0f`(원래 크기에 비례하여), 명암 `4b`(75), 밝기 `32`(50), 효과 `00`, BinItem ID `01 00`이다. 한글에서 밝기 50, 명암 75로 지정했으므로 명암이 먼저다(정정 11).
- 그림 효과 값은 `0`만 봤고, 명암·밝기의 음수는 확인하지 않았다.

### E10. 마지막 1바이트 (`experiments/fill-trailing-unknown-byte`)

이미지 채우기 파일에서 마지막 1B만 `50`, `128`, `255`로 바꿨다. 셋 다 원본과 표시가 같았다. 한글에는 셀 채우기 투명도 설정도 없다. rhwp 정오표 8번은 이를 투명도로 보지만, 이 환경에서는 표시에 영향이 없으므로 의미를 확정하지 않는다.

### E11. 여러 채우기 종류 (`experiments/fill-multi-kind-priority`)

한글 UI는 채우기를 하나만 고르게 하고, 저장할 때도 하나만 남긴다. 다른 종류로 바꿔 저장하면 이전 블록이 지워지고, 그림에서 다른 종류로 바꾸면 BinData의 그림도 지워진다.

여러 비트를 켠 파일(종류 3, 5, 6, 7)도 오류 없이 열렸고, 결과는 3→이미지, 5→그러데이션, 6→이미지, 7→이미지였다. 즉 **이미지 > 그러데이션 > 단색**이다. 블록은 단색, 그러데이션, 이미지 순으로 넣었고, 마지막 1B는 켜진 종류마다 하나씩 넣었다(rhwp 기준). 일곱 파일이 모두 정상으로 열렸으므로 이 배치는 한글과 어긋나지 않는다. 다만 한글이 직접 저장한 복수 종류 파일은 없으므로, 마지막 1B가 종류마다 붙는다는 것은 확정이 아니다.

결과가 본문에 그려진 모습인지 속성 창 값인지는 구분해 기록하지 않았다.

### E14. 문단 머리 정보와 속성 비트

**레코드 구조**: 저장소의 HWP 파일에서 `HWPTAG_NUMBERING` 63개를 직접 읽었다. 모두 수준마다 머리 정보 12B, 번호 형식 길이, 번호 형식 문자열 순으로 7회 읽혔고, 문자열이 `^1.`부터 `^7`까지 수준 순서와 맞았다(정정 25, 26). 한 레코드는 230B였고, 7개 수준과 시작 번호 UINT16까지 읽으면 144B다. 나머지 86B(수준별 시작번호, 확장 수준 8~10)는 E15에서 확인했다.

**속성 비트**: 한글 기본 개요 번호(`1. / 가. / 1) / 가) / (1) / (가) / ①`)의 1, 2, 7수준 속성은 `0x0C`, `0x10C`, `0x2C`였다. bit 5부터 읽으면 0, 8, 1로 표 41의 1,2,3 / 가,나,다 / ①②③과 맞는다. 이후 한글에서 설정을 바꿔 저장하고 바이트와 설정 창을 비교했다.

| 설정 창                      | 저장된 값                                      |
| ---------------------------- | ---------------------------------------------- |
| 번호 모양 ㊀㊁㊂             | 속성 `0x1CC`, bit 5~9 = 14                     |
| 정렬 오른쪽                  | bit 0~1 = 2                                    |
| 번호 너비를 자릿수에 맞춤 끔 | bit 2 = 0                                      |
| 자동으로 내어쓰기 끔         | bit 3 = 0                                      |
| 너비 조정 20.0 mm            | 너비 보정값 5669 (HWPUNIT)                     |
| 본문과의 간격 50 %           | bit 4 = 0, 거리 50                             |
| 본문과의 간격 10 mm          | bit 4 = 1, 거리 2834. 다시 열면 28.3 pt로 표시 |
| 글자 모양 지정 켬            | 글자 모양 아이디 7. 끈 수준은 `0xFFFFFFFF`     |

속성 비트를 직접 바꾼 사본도 열었다.

- bit 5~9를 16으로 바꾸자 甲, 乙, 丙으로 표시됐다(정정 27, 28).
- bit 4만 켜고 거리를 70으로 두자 본문과의 간격이 0.7 pt로 표시됐다(정정 29).
- bit 10~31을 켠 결과와 범위 밖 값(번호 형식 17 이상, 정렬 3)의 처리는 `hangul-behavior.md`에 있다. bit 10 이상의 의미는 확인하지 못했다.

- BIN0003.jpg 스트림과 그 BinData 레코드가 없어졌다.

**확인하지 않은 것**

- 이미지 정보 1B 세 개의 순서(명세는 대비, 밝기, 효과). 실물에서 모두 0이었다.
- 이미지 여부 1, ID 0인 레코드(`id-0x0103-resaved.hwp`)를 한글이 어떻게 표시하는지.

### E19. 문단 수준 (정정 41, 42)

| 5.1.2.0   |   58 |                               |

58B는 5.0.5.0보다 크고 5.1.0.1 이하인 버전에서 생겼다. 그 사이 버전의 파일은 없었다. 5.0.3.3의 46B는 앞뒤 버전과 맞지 않고, 명세의 속성 3·새 줄 간격 조건(5.0.2.5 이상)과도 맞지 않는다. 그래서 길이는 FileHeader 버전이 아니라 레코드 길이로 판단한다.

### E20. 줄 간격의 단위와 옛 줄 간격 칸 (정정 43, 44)

Windows용 한글에서 줄 간격 종류를 바꿔 저장하며 hwp-watch로 봤다. 앱 버전은 기록하지 않았다. 값은 종류를 고르면 한글이 채우는 기본값을 그대로 썼다.

| 설정              | 옛 칸 (속성 1 bit 0~1 / 오프셋 24) | 새 칸 (속성 3 bit 0~4 / 오프셋 50) |
| ----------------- | ---------------------------------- | ---------------------------------- |
| 글자에 따라 160%  | 0 / 160                            | 0 / 160                            |
| 고정 값 16.0pt    | 1 / 3200                           | 1 / 3200                           |
| 여백만 지정 6.0pt | 2 / 1200                           | 2 / 1200                           |
| 최소 16.0pt       | 0 / 100                            | 3 / 3200                           |

길이로 넣는 종류는 여백과 같이 HWPUNIT의 2배다(정정 43). 옛 칸은 최소를 표현하지 못해서 한글은 글자에 따라 100%를 쓴다(정정 44).

macOS 한글에서 새 문서를 만들어 최소(기본값 16.0pt)를 고르고 HWP로 저장해도 같았다. 파일 버전은 5.1.1.0, 문단 모양은 58B였고 옛 칸 0 / 100, 새 칸 3 / 3200이었다. 앱 버전은 기록하지 않았다.

실제 파일 137개의 54·58B 문단 모양에서 최소 레코드 37개는 새 칸 값(1000, 2400, 2500, 2600, 3200)과 관계없이 옛 칸이 모두 0 / 100이었다. 글자에 따라 레코드 5,567개는 두 칸이 모두 같았다. 고정 값과 여백만 지정은 실제 파일에 없어서 위 실험 한 번이 근거다.

**확인하지 않은 것**

- 기본값이 아닌 값. 특히 고정 값·여백만 지정에서도 옛 칸이 새 칸과 늘 같은지.

**개발 전제**: 46B 레코드를 쓰던 한글 2007에는 줄 간격 최소가 없었던 것으로 본다. 한글 2007을 구할 수 없어 확인하지 못했다. 실제 46B 레코드 244개는 모두 옛 칸 종류가 0이었다.

#### 한글이 두 칸 중 어느 쪽을 읽는가

두 칸에 서로 다른 값을 넣고 macOS 한글에서 문단 모양 창에 나오는 값을 봤다. 앱 버전은 기록하지 않았다. 5.0.2.5 파일(문단 모양이 모두 46B)에서 문단 모양 하나를 58B로 늘려 새 칸을 붙였고, 5.1.1.0 파일(58B)은 옛 칸만 바꿨다. 코덱을 거치지 않고 레코드 바이트만 고쳤다. 기반 파일이 저장소에 넣을 수 없는 자료라서 실험 파일은 커밋하지 않았다. 늘리는 스크립트는 `experiments/scripts/widen-para-shape.ts`다.

| 파일 버전 | 옛 칸    | 새 칸    | 창에 나온 값      | 읽은 칸 |
| --------- | -------- | -------- | ----------------- | ------- |
| 5.0.2.5   | 0 / 300  | 없음     | 글자에 따라 300%  | 옛 칸   |
| 5.0.2.5   | 0 / 100  | 0 / 300  | 글자에 따라 100%  | 옛 칸   |
| 5.0.2.5   | 2 / 1200 | 0 / 300  | 여백만 지정 6.0pt | 옛 칸   |
| 5.0.2.5   | 0 / 100  | 1 / 3200 | 고정 값 16.0pt    | 새 칸   |
| 5.0.2.5   | 1 / 1600 | 1 / 3200 | 고정 값 16.0pt    | 새 칸   |
| 5.0.2.5   | 0 / 100  | 3 / 3200 | 최소 16.0pt       | 새 칸   |
| 5.1.1.0   | 0 / 300  | 0 / 160  | 글자에 따라 160%  | 새 칸   |

5.0.2.5 파일에서 한글은 새 칸 종류가 0이 아니면 새 칸을, 0이면 옛 칸을 읽었다. 종류와 값은 늘 같은 칸에서 왔다. 5.1.1.0 파일에서는 새 칸 종류가 0이어도 새 칸을 읽었다. 그래서 이 규칙은 FileHeader 버전에 따라 다르다. 5.0.2.5와 5.1.1.0 사이 어느 버전에서 바뀌는지는 확인하지 않았다.

**두 칸이 다른 파일을 한글이 저장하면**: 위 표의 셋째 줄 파일(5.0.2.5, 옛 칸 2 / 1200, 새 칸 0 / 300)을 macOS 한글에서 열고, 문단 모양은 건드리지 않은 채 본문에 글자를 넣었다 되돌린 뒤 같은 이름으로 저장했다. 앱 버전은 기록하지 않았다.

|           | 파일 버전 | 문단 모양 길이    | 옛 칸    | 새 칸    |
| --------- | --------- | ----------------- | -------- | -------- |
| 원본      | 5.0.2.5   | 46B 57개, 58B 1개 | 2 / 1200 | 0 / 300  |
| 한글 저장 | 5.1.1.0   | 58B 58개          | 2 / 1200 | 2 / 1200 |

한글은 자기가 읽은 칸(여기서는 옛 칸)의 값으로 두 칸을 짝 맞춰 썼다. 원본의 어긋난 칸은 보존하지 않았다. 그래서 코덱은 한글이 읽는 칸을 읽고, 쓸 때 두 칸을 짝 맞춘다. 어긋난 파일의 왕복 기대값도 원본이 아니라 이 결과다. 이번에 직접 저장해 본 것은 이 한 파일이고, 다른 조합도 같은 방식으로 짝 맞출 것이라고 본다.

한글은 이때 파일 버전을 5.1.1.0으로, 46B 문단 모양을 모두 58B로 올렸다. 문단 모양 오프셋 32(테두리/배경 ID)도 모든 레코드에서 1씩 커졌다(0 → 1, 1 → 2). 원인은 확인하지 않았다. 코덱은 이 형식 올리기를 따르지 않는다.

58B 레코드가 섞인 5.0.2.5 파일은 오류 없이 열렸다. 화면은 다섯 파일 모두 기반과 같았다. 한글은 파일을 열 때 줄 배치를 다시 계산하지 않고 본문에 저장된 줄 배치(LINE_SEG)로 그리기 때문이다. 문단 모양 창에서 설정을 누르면 그때 줄 간격이 적용됐다.

### E21. 공백 최소값 (정정 45)

문단 모양 창의 공백 최소값을 바꿔 저장하며 hwp-watch로 봤다. 앱 버전은 기록하지 않았다. 바뀐 것은 속성 1 오프셋 1 바이트(bit 8~15)뿐이고, bit 8(줄 격자)은 켜진 채였다.

| 설정 | 오프셋 1 바이트 | bit 9~15 |
| ---- | --------------- | -------- |
| 100% | `01`            | 0        |
| 99%  | `03`            | 1        |
| 98%  | `05`            | 2        |
| 25%  | `97`            | 75       |

25%는 한글이 받는 최솟값이다. 명세의 0%~75%는 저장 값의 범위와 맞는다.

실제 파일 154개의 문단 모양 6,727개에서 이 칸이 0이 아닌 레코드는 1,025개였고 값은 20, 50, 40, 65, 30, 75, 25(공백 최소값 80, 50, 60, 35, 70, 25, 75%)뿐이었다. 75를 넘는 값은 없었다.

**확인하지 않은 것**

- 75를 넘는 값을 넣은 파일을 한글이 어떻게 읽는지.

## 2026-11-16 실험 기록: 문단 헤더 (표 58, 59)

### E22. 레코드 레벨, 문단 헤더, 단 나누기 종류

**실제 파일 측정**: 저장소의 HWP 99개, 본문 스트림 115개, 레코드 43,354개를 읽었다. 문단은 본문 최상위와 표 셀의 리스트만 셌다.

- 레벨이 앞 레코드보다 2 이상 깊어지는 곳은 없었다. 레벨을 깊이로 보고 앞에서 가장 가까운 한 단계 얕은 레코드를 부모로 삼으면 트리가 하나로 정해진다.
- 문단 리스트 7,527개 모두 text bit 31이 마지막 문단에만 켜져 있었다(정정 50).
- 레벨과 관계없이 모든 문단 9,326개에서 control mask가 PARA_TEXT의 제어 문자에서 13을 뺀 조합과 같았다(정정 51). 글자 모양·range tag·줄 정보 수도 모두 자식 레코드의 항목 수와 같았다.
- 단 나누기 종류 0x02가 켜진 문단 128개 모두 `cold`를 가졌다. 0x01이 켜진 문단 115개는 모두 구역 첫 문단이고 `secd`를 가졌다(정정 52).
- 표 셀 LIST_HEADER 7,412개 모두 자식이 없었고, 셀 문단은 LIST_HEADER와 같은 레벨에 있었다(정정 53).

**한글 실험**: Windows용 한컴오피스 한글 13.0에서 나누기를 넣고 저장하며 hwp-watch로 봤다. 빌드 번호는 기록하지 않았고 실험 파일은 보관하지 않았다. 나누기는 [쪽] 메뉴로 넣었다.

| 조작 | 나누기가 걸린 문단의 단 나누기 종류 |
| ---- | ----------------------------------- |
| 새 문서 저장 | 첫 문단 `0x03` |
| 쪽 나누기 | `0x04` |
| 2단으로 바꾼 뒤 단 나누기 | `0x08` |
| 다단 설정 나누기 | `0x02`. 그 문단에 `cold`가 들어간다 |
| 구역 나누기 | 새 스트림 `Section1`이 생기고 첫 문단이 `0x03`이다 |

나누기 두 개를 한 문단에 겹쳐 넣는 실험(쪽 뒤에 다단 설정, 다단 설정 뒤에 쪽, 단 뒤에 쪽)에서 한글은 매번 문단을 나눴다. 0x06, 0x0C 같은 조합은 만들지 않았다. 동작은 `hangul-behavior.md`에 있다.

## 2026-11-17 실험 기록: 구역 정의 (표 129~136)

### E23. 구역 정의, 각주/미주 모양, 쪽 테두리/배경

**실제 파일 측정**: 저장소의 HWP 99개에 있는 `secd` 115개와 그 자식 레코드를 읽었다. CFB minor 버전이 모두 0x3E로, 한글이 저장한 파일이다.

- `secd` CTRL_HEADER 페이로드는 ctrlId 4B + 명세 26B 뒤에 5.0.2.5 파일 30개는 8B, 5.0.4.0 이상 85개는 17B가 더 있었다(정정 55). 남는 바이트는 한 파일(아래 실험 파일)의 다섯 번째 바이트 `01`을 빼면 모두 0이었다.
- 속성(표 130)은 115개 모두 0이었다. 단 사이 간격 1134, 기본 탭 간격 8000, 줄맞춤·시작 번호·대표 언어 0이었다.
- 자식은 115개 모두 `PAGE_DEF, FOOTNOTE_SHAPE ×2, PAGE_BORDER_FILL ×3` 순서였다. 바탕쪽은 없었다. PAGE_DEF는 모두 40B, 속성 0이었다.
- FOOTNOTE_SHAPE는 230개 모두 28B였다. 구분선 길이를 4B로 읽으면 각주는 길이 `0xFFFFFFFF`, 위·아래·사이 여백 850·567·283(3·2·1mm)이고, 미주는 길이 14,692,344 또는 0, 사이 여백 0이다(정정 59). 속성은 모두 0이었다.
- PAGE_BORDER_FILL은 345개 모두 14B였다(정정 60). 간격은 모두 1417(5mm), 테두리/배경 ID는 1 또는 4이고 5.0.2.5 파일 30개는 0이었다. 1부터 센다는 것은 E25에서 확인했다(정정 67). 그러면 0은 없음이다.

**한글 실험**: 새 문서의 구역 설정 대화상자에서 한 항목씩 바꿔 저장하고 `secd`를 읽었다. 파일 버전은 5.1.2.0이다. Windows용 한글을 썼다. 앱 버전은 기록하지 않았고 실험 파일은 보관하지 않았다.

| 조작 | 속성 | 다른 필드 |
| ---- | ---- | --------- |
| 첫 쪽에만 머리말/꼬리말 감추기, 시작 쪽 번호 사용자 4 | `0x00300003` (bit 0, 1, 20, 21) | 쪽 번호 4 |
| 시작 쪽 번호 이어서 | `0x00000003` | 쪽 번호 0 |
| 시작 쪽 번호 홀수 | `0x00200003` (bit 20~21 = 2) | 쪽 번호 0 |
| 시작 쪽 번호 짝수 | `0x00100003` (bit 20~21 = 1) | 쪽 번호 0 |
| 이어서로 되돌리고 기본 탭 간격 40pt → 30pt | `0x00000003` | 탭 8000 → 6000 |
| 첫 쪽에만 바탕쪽 감추기 | `0x00000007` (bit 2) | |
| 첫 쪽에만 테두리/배경 감추기 | `0x0000001F` (bit 3, 4) | |
| 빈 줄 감추기 | `0x0008001F` (bit 19) | |

단 사이 간격은 대화상자에 11.3pt로 표시됐고 1134였다.

**확인하지 않은 것**

- 표 130 bit 5(쪽 번호 위치, E26에서 확인), bit 8·9(첫 쪽에만 테두리/배경 표시), bit 16~18(텍스트 방향), bit 22(원고지 정서법). 구역 설정 대화상자에는 없는 항목이다.
- 표 132 bit 3 이상, 표 134 속성 전체, 표 136 bit 1~4.
- `secd` 끝 17B의 의미와 한 파일의 `01`.
- 미주 구분선 길이 14,692,344의 의미.

### E24. 현재 쪽만 감추기 (`pghd`, 표 145)

한글의 [현재 쪽만 감추기] 대화상자에서 한 항목만 켜고 저장하기를 여섯 번 반복했다. E23과 같은 파일을 이어서 썼다. 파일 버전은 5.1.2.0이다. Windows용 한글을 썼다. 앱 버전은 기록하지 않았고 실험 파일은 보관하지 않았다.

- 구역 정의 속성은 바뀌지 않았다. 대신 커서가 있던 문단의 PARA_TEXT에 제어 문자 21(0x15) 8칸과 `pghd` CTRL_HEADER가 생겼다.
- CTRL_HEADER 페이로드는 매번 8B였다: ctrlId 4B 뒤 속성 4B(정정 62).

| 감출 내용 | 속성 |
| --------- | ---- |
| 머리말 | `0x01` |
| 꼬리말 | `0x02` |
| 바탕쪽 | `0x04` |
| 쪽 테두리 | `0x08` |
| 쪽 배경 | `0x10` |
| 쪽 번호 | `0x20` |

비트 배치가 구역 정의 속성(표 130) bit 0~5와 같다. 그래서 표 130 bit 5는 첫 쪽에서 쪽 번호를 감추는 비트로 보였다. E26에서 확인했다.

**확인하지 않은 것**

- 여러 항목을 함께 켠 값. 비트 OR로 보인다.
- 한 문단에 `pghd`가 둘 이상 들어가는지.

### E25. 쪽 테두리/배경, 글자 방향, 원고지

E23·E24와 같은 파일을 이어서 썼다. Windows용 한글, 파일 버전 5.1.2.0. 앱 버전은 기록하지 않았고 실험 파일은 보관하지 않았다. 시작 상태의 구역 정의 속성은 `0x0008001F`였다.

**쪽 테두리/배경 대화상자**: 테두리 탭에서 실선 0.1mm 검정 테두리를 "양쪽"에 넣으며 시작했다.

| 조작 | 구역 정의 속성 | 첫 번째 PAGE_BORDER_FILL 속성 |
| ---- | -------------- | ----------------------------- |
| 테두리 적용 쪽 "첫 쪽만" (대화상자는 "첫 쪽 제외"로 열렸다) | `0x00080117` (bit 3 꺼짐, bit 8 켜짐) | `0x01` |
| 위치 "종이 기준" | 그대로 | `0x00` |
| 위치 "쪽 기준", 머리말 포함 | 그대로 | `0x03` |
| 꼬리말 포함만 | 그대로 | `0x05` |
| 테두리 적용 쪽 "모두" | `0x00080017` (bit 8 꺼짐) | 그대로 |
| 배경 탭: 그러데이션, 적용 쪽 "첫 쪽만" | `0x00080207` (bit 4 꺼짐, bit 9 켜짐) | 그대로 |
| 배경 채울 영역 "쪽" | 그대로 | `0x0D` |
| 배경 채울 영역 "테두리" | 그대로 | `0x15` |

- 테두리를 넣자 첫 번째 PAGE_BORDER_FILL의 테두리/배경 ID가 1에서 3이 됐다. 문서 정보의 세 번째 테두리/배경이 새 실선 테두리였다. 배경을 넣자 그 레코드가 40B에서 71B로 커졌고 ID는 그대로였다.
- 1쪽 문서에서 "홀수 쪽"에 테두리를 넣고 저장했을 때는 세 레코드가 바뀌지 않았다. 쪽 나누기로 3쪽을 만들고 홀수 쪽에 점선을 넣자 세 번째 레코드의 ID가 바뀌었다. 짝수 쪽에 일점쇄선을 넣자 두 번째 레코드의 ID가 바뀌었다(정정 67). 두 번째 시도에서는 적용 범위와 선 종류도 바꿨으므로 쪽 수만이 원인이라고 단정하지 않는다.
- 저장할 때마다 한글이 문서 정보의 테두리/배경 순서를 다시 매기고, 쓰이지 않는 레코드를 지우고, PAGE_BORDER_FILL의 ID를 고쳐 썼다.

**글자 방향**: [쪽] → 글자 방향에서 고르고 저장했다. 구역 정의 속성은 바뀌지 않았다. 표 129의 26B 뒤 영역 4~7번째 바이트(CTRL_HEADER 페이로드 오프셋 34)를 UINT32로 읽은 값이 바뀌었다(정정 64).

| 글자 방향 | UINT32 |
| --------- | ------ |
| 가로쓰기 | `0x00000001` |
| 세로쓰기(영문 눕힘) | `0x00020001` |
| 세로쓰기(영문 세움) | `0x00040001` |
| 가로쓰기로 되돌림 | `0x00000001` |

bit 0의 `1`은 E23 샘플 115개 중 이 파일에만 있었고, 아래 원고지 문서에서도 0이었다. 의미는 모른다.

**원고지**: [쪽] → 원고지에서 "200자 원고지(A4 용지)-검정"으로 새 문서를 열어 저장했다. 내용 채우기는 껐다.

- 구역 정의 속성 `0x20400000`(bit 22, 29). 세로·가로 줄맞춤 3713, 2863. 용지 설정 속성 bit 0(넓게)이 켜졌다.
- `secd`의 자식에 쪽 테두리/배경 다음으로 LIST_HEADER(34B)와 문단 하나가 더 있었다. 그 문단에 원고지 칸 표(`tbl `)와 자동 번호(`atno`)가 있었다. 바탕쪽으로 보인다(정정 68).

**확인하지 않은 것**

- 구역 정의 속성 bit 5. 켜는 UI를 찾지 못했다. 감추기(표 145)의 0x20(쪽 번호)과 같은 자리다. 뜻은 E26에서 확인했다.
- 글자 방향이 든 UINT32의 경계와 bit 0. E27에서 확인했다.
- bit 22와 bit 29를 각각 켜는 조작.
- 바탕쪽 LIST_HEADER의 필드 배치와 양쪽·홀수·짝수 바탕쪽이 여럿일 때의 순서.

### E26. 구역 정의 속성 bit 5

E23~E25에서 켜는 UI를 찾지 못한 bit 5를 비트만 바꿔 확인했다. Windows용 한글 2024, 파일 버전 5.1.2.0. 앱 버전은 기록하지 않았다. 실험 파일은 `experiments/section-bit-5`에 있다.

한글 새 문서에 쪽 나누기로 세 쪽을 만들고 쪽 번호 매기기(가운데 아래)를 넣어 저장했다. 구역 정의 속성은 `0x00000000`이었다. 이 파일의 `secd` 속성에서 bit 5만 켜고 한글에서 열었다.

| 속성 | 1쪽 | 2쪽 | 3쪽 |
| ---- | --- | --- | --- |
| `0x00000000` (대조) | `- 1 -` | `- 2 -` | `- 3 -` |
| `0x00000020` | 없음 | `- 2 -` | `- 3 -` |

- 구역 설정 대화상자에는 bit 5에 해당하는 항목이 없었다. [설정]을 누르고 저장해도 속성은 `0x00000020`으로 남았다.
- 그러므로 bit 5는 구역의 첫 쪽에서 쪽 번호를 감춘다(정정 69). bit 0~5가 감추기(표 145)와 같은 배치다.

**확인하지 않은 것**

- 머리말·꼬리말 안의 쪽 번호 필드도 감추는지.
- 인쇄·PDF 출력.
- 구역이 둘 이상일 때.

### E27. 구역 정의의 글자 방향 필드

E25에서 확인하지 않은 글자 방향 필드의 경계와 같은 영역의 다른 바이트를 확인했다. Windows용 한글 2024, 파일 버전 5.1.2.0. 앱 버전은 기록하지 않았다. 실험 파일은 `experiments/section-text-direction`에 있다. 오프셋은 CTRL_HEADER 페이로드 기준이다(표 129 오프셋 + 4).

**한글에서 저장**: 새 문서에 "가나다 ABC 123"을 입력하고 [쪽] → 글자 방향 → 글자 방향 설정에서 항목을 바꿔 저장했다.

| 설정 | 바이트 34~37 |
| ---- | ------------ |
| 가로쓰기 | `01 00 00 00` |
| 영문 눕힘 | `01 00 02 00` |
| 영문 눕힘, 머리말/꼬리말에 세로쓰기 적용 | `01 00 12 00` |
| 영문 세움 | `01 00 04 00` |

영문 세움으로 저장한 HWPX의 `hp:secPr`은 `textDirection="VERTICALALL"`, `memoShapeIDRef="1"`, `textVerticalWidthHead="0"`이었다.

**비트만 켜서 열기**: 가로쓰기 파일의 바이트 36을 바꿔 한글에서 열었다.

| 바이트 36 | 본문 | 대화상자 |
| --------- | ---- | -------- |
| `0x01` | 가로 | 가로쓰기 |
| `0x02` | 세로 | 영문 눕힘 |
| `0x06`, `0x08` | 세로, 영문이 서 있음 | 종류 선택 없음 |
| `0x10` | 가로 | 가로쓰기, 머리말/꼬리말 체크(비활성) |
| `0x20`, `0x80` | 가로 | 가로쓰기 |

바이트 37을 `0x01`로 바꾼 파일도 가로였다. 모든 파일을 다시 저장해도 바꾼 바이트가 그대로 남았다.

- 글자 방향은 바이트 36(표 129 오프셋 32)의 bit 1~3이다(정정 64). 바이트 34부터 UINT32로 읽으면 bit 17~19다. E25에서 적은 bit 16~18은 한 칸 어긋나 있었다.
- 바이트 36 bit 4는 머리말/꼬리말 세로쓰기다(정정 70).
- 바이트 34는 E25에서 본 bit 0이다. 저장소 HWP 구역 120개 가운데 이 바이트가 1인 5개는 모두 문서 정보에 메모 모양(MEMO_SHAPE)이 하나 있었다. 0인 115개는 메모 모양이 없었다. HWPX의 `memoShapeIDRef="1"`과 함께 보면 메모 모양 ID로 보였다. E28에서 확인했다.

**확인하지 않은 것**

- 메모 모양 ID의 길이와 바꿨을 때의 효과. E28에서 확인했다.
- 글자 방향 필드의 위쪽 경계. E28에서 바로 앞의 메모 모양 ID가 2B로 끝나는 것은 확인했다.
- 머리말/꼬리말 세로쓰기가 실제 머리말 모양에 주는 효과.

### E28. 구역 정의의 메모 모양 ID

E27에서 추정한 메모 모양 ID를 확인했다. Windows용 한글 2024, 파일 버전 5.1.2.0. 앱 버전은 기록하지 않았다. 실험 파일은 `experiments/section-memo-shape-id`에 있다. 오프셋은 CTRL_HEADER 페이로드 기준이다.

한글 새 문서의 두 구역에 메모를 하나씩 넣었다. 둘째 구역에서 메모 모양 대화상자의 너비를 80mm로 바꾸고(적용 범위 "현재 구역") 저장했다. 문서 정보에 메모 모양이 55mm, 80mm 두 개 생겼다. 두 레코드는 첫 4B(너비)만 달랐다. 첫 구역의 바이트 34~35는 `01 00`, 둘째 구역은 `02 00`이었다.

첫 구역의 값을 바꿔 한글에서 열고, 1쪽과 2쪽의 메모 칸 너비를 비교했다.

| 바이트 34~35 | 1쪽 메모 칸 | 다시 저장한 값 |
| ------------ | ----------- | -------------- |
| `01 00` (대조) | 55mm | — |
| `02 00` | 80mm | — |
| `00 00` | 55mm | `00 00` |
| `03 00` | 55mm | `00 00` |
| `02 01` | 55mm | `00 00` |

다시 저장한 파일은 모두 문서 정보의 메모 모양이 80mm 하나로 줄었고, 둘째 구역의 값이 `01 00`이 됐다.

- 표 129 오프셋 30은 메모 모양 ID다. 문서 정보의 메모 모양을 1부터 가리킨다(정정 70).
- 길이는 2B다. `02 01`이 ID 2로 그려지지 않았고, 다시 저장하면 0이 됐다. 바로 뒤 오프셋 32는 글자 방향 속성이므로(E27) 4B가 아니다.
- 0과 범위 밖의 값은 메모 모양 없음으로 다룬다. 다시 저장하면 0으로 쓴다.
- 한글은 저장할 때 어느 구역도 가리키지 않는 메모 모양을 지우고 ID를 다시 매긴다.

**확인하지 않은 것**

- 0일 때 쓰는 55mm가 한글 기본값인지 첫 메모 모양인지. 이 문서에서는 둘이 같았다.

### Windows에서 후속 확인할 사항

- bit 10만 켜고 끄면서, bit 8/9와 독립적인 효과가 있는지 확인한다.
- Slash·BackSlash 모양 `000/010/011/110/111`을 각각 고정된 조건에서 비교한다. 특히 macOS에서 같아 보인 `011`과 `110`의 차이를 확인한다.
- 중심선 bit 13, 회전 bit 11/12를 각각 켠 조건에서도 꺾임 bit 8/9의 역할을 확인한다.
- 일반 선 종류 14~17의 3D 계열이 표시되는 조건과 값별 모양을 확인한다.
- 대각선 선 종류를 점선 이외의 값(특히 `0`, `2`)으로 바꿔 E6의 대응을 확인한다.
- 그러데이션 색을 3개 이상 지정해, 위치 배열(`INT32 × num`)의 배치를 확인한다(E7).

### 보강 참고 자료

[rhwp 프로젝트의 HWP 5.0 정오표](https://github.com/edwardkim/rhwp/wiki/HWP-5.0-Spec-Errata)는 종류·굵기·색상의 인터리브 배치와 `0=None, 1=Solid` 열거값을 기록한다. 이는 오늘 독립적으로 확인한 E1·E2를 보강하는 자료다. 한컴 공식 정오표는 아니며, 이 페이지에는 E3·E4의 대각선 비트에 대한 정정이 없다.

## 2026-11-18 실험 기록: 문단의 영역 태그 (표 63)

### E29. 형광펜

저장소의 HWP 133개(문단 9,607개)에는 PARA_RANGE_TAG가 하나도 없었다. Windows용 한글 2024 새 문서에 `AAAA BBBB CCCC`를 입력하고 기능을 하나씩 더해 저장했다. 앱 버전은 기록하지 않았다. 실험 파일은 `experiments/range-tag-highlight`에 있다. 위치는 PARA_TEXT 코드 단위이고, 구역 첫 문단이라 `secd`·`cold` 16칸 뒤인 16부터 `AAAA`다.

| 조작 | PARA_RANGE_TAG (시작–끝, 종류, 데이터) |
| --- | --- |
| `BBBB`(21~24)에 노란 형광펜 | `21–25`, 2, `0x00FFFF` |
| `CCCC`(26~29)에 빨간 형광펜, `AA BB`(18~22)에 초록 형광펜을 노란 구간과 겹쳐 칠함 | `18–23`, 2, `0x008000` / `23–25`, 2, `0x00FFFF` / `26–30`, 2, `0x0000FF` |
| 첫 `AA`에 교정 부호 뺌표 | 위 세 항목이 그대로 16씩 밀림 |
| 변경 내용 추적을 켜고 줄 끝에 글자 입력 | 그대로 |

- 형광펜이 종류 2다. 데이터는 COLORREF(`0x00BBGGRR`)의 아래 3바이트로, 같은 문서를 HWPX로 저장하면 `<hp:markpenBegin color="#FFFF00"/>`였다(정정 72).
- 끝 위치는 구간 밖이다. 네 글자 `BBBB`가 `21–25`였다.
- 겹쳐 칠하면 나중 색이 이기고 앞 구간이 잘린다. 항목끼리 겹치지 않고 시작 위치 순서로 저장된다.
- 뺌표는 PARA_TEXT에 필드 시작(0x03, `%%*C`)과 필드 끝(0x04)으로 들어갔다. 위치에는 이 컨트롤의 8칸씩이 그대로 더해졌다.
- 변경 내용 추적으로 넣은 글자는 영역 태그를 만들지 않았다. 추적 정보가 어디에 저장되는지는 보지 않았다.

**교정 부호 20가지**: 새 문서의 20줄에 교정 부호 대화상자의 부호를 하나씩 넣었다(`proofread-all.hwp`). 영역 태그는 하나도 생기지 않았다. 모두 필드였고 CTRL_HEADER ctrlId는 `%unk`, 필드 시작 문자 뒤의 ctrlId가 부호마다 달랐다.

| 교정 부호 | 필드 시작 문자의 ctrlId |
| --- | --- |
| 고침표, 뺌표, 지움표, 붙임표, 줄 붙임표, 줄 이음표 | `%%*c`, `%%*C`, `%%*d`, `%%*a`, `%%*A`, `%%*i` |
| 톱니표, 생각표, 칭찬표, 줄표 | `%%*S`, `%%*T`, `%%*P`, `%%*L` |
| 자리 바꿈표, 줄 서로 바꿈표, 오른 자리 옮김표, 왼 자리 옮김표 | `%%*n`, `%%*t`, `%%*r`, `%%*l` |
| 메모 고침표 | `%%mr` (메모가 함께 생긴다) |
| 넣음표, 띄움표, 부호 넣음표, 줄 바꿈표, 줄 비움표 | 모두 `%sig`. 커서 자리의 빈 필드다 |

- 줄 이음표와 줄 서로 바꿈표의 필드는 문단 경계를 넘는다. 시작 문자와 끝 문자가 서로 다른 문단에 있다. 줄 서로 바꿈표는 둘째 문단 맨 앞에 빈 필드 `%spl`도 만들었다.
- 그러므로 한글 2024 UI로 만들 수 있는 영역 태그는 형광펜(종류 2)뿐이었다.
- 코덱으로 다섯 파일을 읽고 다시 쓰면 BodyText 레코드가 모두 원본과 바이트까지 같았다.

**확인하지 않은 것**

- 종류 2 말고 다른 값을 쓰는 기능. 한글 2024보다 오래된 버전이 교정 부호를 영역 태그로 저장했는지. 변경 내용 추적의 지우기.
- 교정 부호 필드의 CTRL_HEADER 명령과 `%sig` 다섯 가지를 구분하는 값.
- 여러 문단에 걸친 형광펜.
- 겹치는 구간, 끝 < 시작 같은 값을 넣은 파일을 한글이 어떻게 여는지.

## 2026-11-18 실험 기록: 개체 공통 속성 (표 67, 69, 70)

### E30. 표·사각형의 개체 공통 속성

Windows용 한글 2024 새 문서에 2×2 표를 넣고, 표/셀 속성 대화상자에서 값을 바꿔 가며 저장했다. 마지막 파일에는 사각형도 그렸다. 앱 버전은 기록하지 않았다. 실험 파일은 `experiments/object-common-props`에 있다. 오프셋은 ctrlId를 포함한 CTRL_HEADER 페이로드 기준이다.

| 파일 | 대화상자 | 속성(오프셋 4) | 오프셋 40 |
| --- | --- | --- | --- |
| `table-wrap-square` | 크기 고정, 어울림, 본문 위치 오른쪽, 가로 쪽 가운데 12mm, 세로 쪽 아래 34mm, 번호 종류 그림, 개체 보호 | `0x461A2548` | 0 |
| `table-topbottom-para` | 자리 차지, 세로 문단 위 5mm, 쪽 영역 제한 끔, 조판 부호와 같은 쪽 켬 | `0x463A0510` | 1 |
| `table-behind-para` | 글 뒤로 | `0x465A0510` | 1 |
| `shape-rect-desc`의 사각형 | 기본값(글 앞으로, 종이 기준, 겹침 허용), 설명문 `Desc가나` | `0x046A4000` | 0 |

### E34. 캡션 LIST_HEADER의 세로 정렬

### E36. 쪽 경계에서 나눔 값과 명세에 없는 비트

Windows용 한글 2024에서 2×2 표를 만들고 표/셀 속성 대화상자의 "표" 탭을 하나씩 바꿔 HWP와 HWPX로 저장했다(`experiments/table-property-bits`). 대화상자는 computer use로 조작했다.

| 대화상자 "쪽 경계에서" | bit 0~1 | HWPX `pageBreak` |
| --- | --- | --- |
| 나눔(새 표 기본값) | 2 | `CELL` |
| 셀 단위로 나눔 | 1 | `TABLE` |
| 나누지 않음 | 0 | `NONE` |

제목 줄 자동 반복은 bit 2와 `repeatHeader`였다. "자동으로 나뉜 표의 경계선 설정"은 속성 비트가 아니라 표의 테두리/배경 참조(`borderFillIDRef` 3 → 4)를 바꿨다(정정 88).

명세에 없는 비트는 기반 파일에 하나씩 켜고 한글로 열어 다시 저장했다.

| 비트 | 다시 저장한 HWP | HWPX |
| --- | --- | --- |
| 3 | 유지 | `noAdjust="1"` |
| 24 | 지워짐 | 변화 없음 |
| 25 | 유지 | 변화 없음 |
| 26 | 유지 | 변화 없음 |

대화상자로 만든 새 표는 bit 24~26이 0이었고, 첫 셀에 글자를 입력해 저장하자 bit 26이 켜졌다. 글자처럼 취급, 줄 높이 바꾸기, 너비 "단에 맞춤"으로 만든 표는 이 비트들을 바꾸지 않았다. 한글 자동화로 만든 표(`experiments/list-header-properties/base-2cell.hwp`)에는 bit 24가 켜져 있었다.

저장소 HWP의 표 464개에서는 bit 3이 켜진 167개가 모두 글자처럼 취급이고 줄 높이가 서로 달랐다. bit 25가 켜진 148개 중 146개가 글자처럼 취급이었다. bit 26이 꺼진 142개 중 병합, 셀 크기 차이, 글자처럼 취급이 있는 표는 1개뿐이었다(`scratch/scan-table-bits-corr.ts`).

**확인하지 않은 것**

- bit 3을 켜는 조작과 `noAdjust`의 실제 동작(KS X 6101 표 194의 "1 pt 보정"이 한글에서 어떻게 나타나는지). bit 25를 켜는 조작.
- bit 24, 25, 26이 화면이나 편집 동작에 주는 영향.
- HWPX로 저장해 bit 25, 26이 사라진 문서를 다시 HWP로 저장했을 때의 값.

## 2026-11-24 측정 기록: 그리기 개체의 테두리 선 (표 81, 86, 87)

### E37. 테두리 선 정보의 길이

한글 2024가 저장한 저장소 HWP 파일의 사각형 SHAPE_COMPONENT(`$rec$rec`, 252바이트)를 모두 읽었다. 그중에는 사용자가 `scratch/test.hwp`에 새로 그린 사각형도 있다. ID 8 + 개체 요소 속성 42 + Rendering 정보 146(행렬 쌍 1개) 뒤에 56바이트가 남았고, 앞부분은 모두 같았다.

```
00 00 00 00   선 색상: 검정
21 00 00 00   선 굵기: 33 (기본값 0.12mm)
41 00 00 d1   속성: 선 종류 1, 끝 모양 1(flat), 화살표 크기 4·4(중간-중간), bit 30·31 채움
00            Outline style: normal
01 00 00 00   채우기 종류: 단색 (표 28)
ff ff ff 00   배경색: 흰색
...
```

명세대로 굵기를 2바이트로 읽으면 속성이 `0x00410000`(선 종류 0), Outline style이 `0x00`, 채우기 종류가 `0x000100d1`이 돼 맞지 않는다. 4바이트로 읽으면 속성의 모든 필드가 한글 기본 사각형의 값(검정 0.12mm 실선)과 맞고, 바로 뒤에 채우기 종류 1(단색)이 온다(정정 89). 그림(`$pic$pic`, 196바이트)은 Rendering 정보에서 레코드가 끝나 테두리 선 정보가 없었다.

**확인하지 않은 것**

- 굵기의 상위 2바이트가 0이 아닌 파일. 그래서 INT32인지 INT16 + 2바이트인지는 구분하지 못했다. 저장소 파일은 굵기가 모두 33이다.
- 실선 밖의 선 종류 번호, 화살표 모양·크기, Outline style을 한글 대화상자에서 바꿨을 때의 값. 명세가 두 번 적은 화살표 크기 8 「큰-중간」이 「큰-큰」인지.

### E39. 채우기 정보 뒤 22바이트

Windows용 한글 2024에서 사각형의 개체 속성 "그림자" 탭을 바꿔 HWP와 HWPX로 저장하고, SHAPE_COMPONENT의 채우기 정보 뒤 22바이트를 HWPX `hp:shadow`, `hp:rect`와 맞춰 봤다(`experiments/shape-shadow`). 대화상자는 computer use로 조작했다.

```
그림자 없음  00 00 00 00 | b2 b2 b2 00 | 00 00 00 00 | 00 00 00 00 | 2a ff cd 0a | 00 | 00
그림자 있음  0d 00 00 00 | b2 b2 b2 00 | 1b 01 00 00 | 36 02 00 00 | 2a ff cd 0a | 00 | 4d
             종류          색            가로 1.0mm    세로 2.0mm    instid        ?    투명도 30%
```

- 가로·세로 이동 283, 566은 HWPX `offsetX`, `offsetY`와 같았다. 투명도 30%는 77(255 × 0.3)이고 HWPX `alpha="77"`과 같았다.
- `2a ff cd 0a`(`0x0ACDFF2A`)는 HWPX `hp:rect`의 `instid="181272362"`와 같았다. 저장소 파일의 한 문서 안 두 사각형은 이 값이 달랐고, 한글로 여러 번 다시 저장해도 바뀌지 않았다.
- 그림자 종류 아이콘 10개는 1~8, 13, 14였고 HWPX 이름은 `PARELLEL_*`, `SHEAR_*`, `SCALE_NARROW`, `SCALE_ENLARGE`였다. 9~12는 대화상자로 만들 수 없었다.
- 글상자가 있는 사각형과 없는 사각형의 22바이트는 인스턴스 ID 말고는 같았다. 글상자의 여백·최대 폭(표 90)은 자식 LIST_HEADER의 8바이트 뒤에 있었다(정정 91).

**확인하지 않은 것**

- 오프셋 20의 바이트(모든 파일에서 0). 그림자 색을 바꾼 파일. 음수 이동. 9~12를 넣은 파일.

## 2026-11-24 실험 기록: 그리기 개체의 채우기 (표 28)

### E40. 채우기 종류 조합과 끝 바이트

Windows용 한글 2024에서 사각형의 개체 속성 "채우기" 탭을 바꿔 HWP로 저장했다(`experiments/shape-fill`). 대화상자의 색 채우기 없음·색·그러데이션은 라디오 버튼이고, 그림은 체크박스라 색이나 그러데이션과 함께 고를 수 있다. 탭 아래에 투명도가 있다.

| 대화상자 | 종류 | 끝 바이트 |
| --- | --- | --- |
| 색 채우기 없음 | 0 | 없음 |
| 색 | 1 | `00` |
| 색, 투명도 30% | 1 | `4d` |
| 그러데이션 | 4 | `00` |
| 색 채우기 없음 + 그림 | 2 | `00` |
| 색 + 그림 | 3 | `00 00` |
| 색 + 그림, 투명도 30% | 3 | `4d 4d` |
| 그러데이션 + 그림, 투명도 30% | 6 | `4d 4d` |

블록 순서는 DocInfo와 같이 색, 그러데이션, 그림이었고, 추가 채우기 속성 뒤에 켜진 종류마다 투명도 1바이트가 있었다(정정 92). 정정 10의 셀 배경 실험에서 이 바이트를 바꿔도 표시가 같았던 것은 셀 배경에 투명도 설정이 없기 때문으로 보인다.

Windows 셀 배경 대화상자("셀 테두리/배경" › 배경)도 같은 구조로, 색 채우기 없음·색·그러데이션 라디오 버튼과 그림 체크박스가 있고 투명도 칸은 없다. macOS 한글 실험(`experiments/fill-multi-kind-priority`)에서 만든 종류 3·5·6·7 셀 배경을 Windows 한글 2024로 열었다.

| 파일 | 그린 것 | 셀 배경 대화상자 | 다시 저장한 BorderFill |
| --- | --- | --- | --- |
| `3-color-image` | 그림 | 색(주황) + 그림 | 원본과 같음 |
| `5-color-gradient` | 그러데이션 | 그러데이션 | 원본과 같음 |
| `6-gradient-image` | 그림 | 그러데이션 + 그림 | 원본과 같음 |
| `7-all` | 그림 | 그러데이션 + 그림 | 원본과 같음 |

네 파일 모두 오류 없이 열렸고, 아무것도 바꾸지 않고 다시 저장한 BorderFill 레코드는 원본과 바이트가 같았다(`windows-2024/`). 대화상자는 라디오 버튼이라 색과 그러데이션이 함께 켜지면 그러데이션만 보였다.

**확인하지 않은 것**

- 두 투명도 바이트를 다르게 넣은 파일. 그러데이션만 켜고 투명도를 바꾼 파일.
- 종류 5·7에서 대화상자의 "설정"을 누른 뒤 저장한 값.

### E41. 투명도 바이트를 바꾼 파일

E40에서 대화상자 투명도가 채우기 끝 바이트에 저장되는 것을 봤다. 그 바이트만 바꾼 파일을 Windows 한글 2024로 열어 화면과 대화상자를 확인했다(`experiments/fill-alpha`).

| 대상 | 바꾼 값 | 결과 |
| --- | --- | --- |
| 빨간 단색 사각형 | 0, 77, 200, 255 | 0은 진한 빨강, 값이 클수록 옅어지고 255는 보이지 않았다. 대화상자는 200을 78%, 255를 100%로 보였다 |
| 빨강 + 파란 그림 사각형 | (색, 그림) = (0, 200) | 그림이 거의 투명해져 빨강이 비쳤다 |
| 같은 사각형 | (200, 0) | 파란 그림만 보였다 |
| 흰색→검정 그러데이션 사각형 | 0, 200, 255 | 200은 옅어지고 대화상자 78%, 255는 보이지 않았다 |
| 그러데이션 + 파란 그림 사각형 | (그러데이션, 그림) = (0, 200), (200, 0) | 그림 200이면 그러데이션이 비치고, 그러데이션 200이면 그림만 보였다 |
| 빨간 셀 배경 | 0, 200, 255 | 셋 다 진한 빨강 |
| 빨간 문단 배경, 파란 쪽 배경, 노란 글자 배경 | 0, 200, 255 | 각각 셋 다 같았다 |

- 값은 투명한 정도다(0 불투명). 두 바이트는 블록 순서대로 각 종류(색 또는 그러데이션, 그림)의 투명도였다(정정 92).
- DocInfo 테두리/배경(셀, 문단, 쪽, 글자)은 투명도를 그리지 않았다. 네 대화상자 모두 투명도 칸이 없다. macOS 한글의 정정 10 실험과 같다.
- 한글로 다시 저장하면 사각형의 200, 셀·문단·쪽·글자 배경의 255가 그대로 남았다.

### E42. 모서리 곡률과 꼭짓점

Windows용 한글 2024에서 사각형의 개체 속성 "선" 탭 "사각형 모서리 곡률"과 크기를 바꿔 HWP로 저장했다(`experiments/shape-rectangle`). 대화상자는 computer use로 조작했다.
