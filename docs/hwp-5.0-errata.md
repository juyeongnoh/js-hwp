## 2026-10-28 실험 기록

이 절은 실제 바이트 검사, 한글 화면에서의 관찰, 미확인 사항을 구분한다. 명세와 다른 표시가 나왔다는 이유만으로 명세의 모든 설명이 잘못됐다고 단정하지 않는다.

- 에이전트가 직접 화면을 확인한 환경: macOS 한글 `12.30.0`, 빌드 `6313`, 읽기 전용 모드.
- 대각선의 개별 조합은 사용자가 실제 한글에서 연 뒤 제공한 캡처로 확인했다. 그 캡처의 앱 버전은 별도로 확인하지 않았다.
- Windows 한글에서의 비교는 별도 후속 작업이다. 아래 macOS 관찰을 Windows의 동작으로 일반화하지 않는다.
- 이 기록에서 HWPX는 HWP 동작을 확정하는 기준으로 사용하지 않는다.

### E1. BorderFill의 실제 바이트 배치

기존 HWP 파일을 CFB 라이브러리로 열고, FileHeader의 압축 플래그에 따라 DocInfo를 압축 해제한 뒤 레코드 헤더와 페이로드를 직접 검사했다. 프로젝트의 HWP 라이터가 만든 파일로 배치를 증명하지 않았다.

| 원본 파일 | BorderFill 레코드 수 |
| --- | ---: |
| sample.hwp | 2 |
| sample2.hwp | 18 |
| sample3.hwp | 574 |
| sample4.hwp | 36 |
| 합계 | 630 |

검사한 레코드는 모두 아래 32바이트 구간을 포함했다. 나머지 바이트에는 채우기 정보 등이 이어진다. 오프셋은 레코드 헤더를 제외한 페이로드 시작 기준이다.

| 오프셋 | 내용 |
| --- | --- |
| 0~1 | 속성 UINT16 |
| 2~7 | 왼쪽: 종류 1B + 굵기 1B + 색상 4B |
| 8~13 | 오른쪽: 같은 6B 구성 |
| 14~19 | 위쪽: 같은 6B 구성 |
| 20~25 | 아래쪽: 같은 6B 구성 |
| 26~31 | 대각선: 종류 1B + 굵기 1B + 색상 4B |

예를 들어 sample3.hwp의 한 레코드는 다음처럼 읽힌다.

```text
00 00                 속성
00 00 FF FF FF FF     왼쪽
00 00 FF FF FF FF     오른쪽
01 00 5B 9B D5 00     위쪽
01 00 5B 9B D5 00     아래쪽
00 00 FF FF FF FF     대각선
```

일반 테두리 네 방향과 대각선은 바이트 길이와 종류 값의 타입이 같다. 대각선도 `BorderLine`(종류는 `LineStyle`)으로 모델링한다. 명세 표 27의 `0=Slash`, `1=BackSlash`, `2=CrookedSlash` 해석은 E6에서 실제 값과 맞지 않는 것을 확인했다.

현재 읽기 구현은 네 방향을 종류·굵기·색상 한 세트씩 읽고, 대각선은 `hasMore(6)`일 때 읽는다. 이는 현재 파서의 처리 정책이며, 잘린 대각선 레코드가 정상이라는 실험 결과는 아니다.

### E2. 일반 테두리선 종류 값

정상적으로 열리는 sample.hwp를 기준으로, 네 방향 선 종류를 0~17로 바꾼 사본 18개를 실제 한글에서 열었다. 굵기와 색상은 동일하게 고정했다. 각 사본의 종류 바이트가 의도한 값인지와 DocInfo 이외의 원본 스트림 보존을 확인했다.

| 실제 값 | 관찰한 표시 또는 추정 이름 | 판정 |
| ---: | --- | --- |
| 0 | 선 없음 | 화면 확인 |
| 1 | 실선 | 화면 확인 |
| 2 | 긴 점선 | 화면 확인 |
| 3 | 점선 | 화면 확인 |
| 4 | 일점쇄선 | 화면 확인 |
| 5 | 이점쇄선 | 화면 확인 |
| 6 | 더 긴 선분의 반복 | 화면 확인 |
| 7 | 원형 점의 반복 | 화면 확인 |
| 8 | 이중선 | 화면 확인 |
| 9 | 가는선 + 굵은선 이중선 | 화면 확인 |
| 10 | 굵은선 + 가는선 이중선 | 화면 확인 |
| 11 | 가는선 + 굵은선 + 가는선 삼중선 | 화면 확인 |
| 12 | 물결 | 화면 확인 |
| 13 | 물결 이중선 | 화면 확인 |

| 17 | 3D 단선, 광원 반대 | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |

14~17은 속성 bit 0의 3D 효과를 켠 사본 4개도 비교했지만 선이 표시되지 않았다. 이 결과만으로 값이 무효이거나 의미가 없다고 결론 내리지 않는다. 추가 속성이나 한글 버전·플랫폼에 따른 표시 조건은 미확인이다.

명세의 실선 이후 항목이 실제 값보다 1 작게 적힌 것은 `선 없음=0` 항목 누락에 따른 차이로 추정한다. 0~13은 관찰로 뒷받침되지만, 3D 계열 전체의 대응까지 시각적으로 확정한 것은 아니다.

시험 중 DocumentBuilder로 새로 생성한 별도 문서는 한글에서 파일 손상 경고가 나왔다. 그 문서는 위 결과에서 제외하고 정상 원본의 바이너리를 직접 변경한 사본으로 검증했다. 생성 문서의 손상 원인은 이번 실험 범위에서 조사하지 않았다.

### E3. bit 8과 bit 9의 독립적인 꺾임 플래그

대각선 샘플 HWP의 첫 행 첫 번째 셀을 대상으로, Slash 모양과 BackSlash 모양을 모두 `010`으로 고정했다. bit 10과 나머지 속성은 고정한 채 bit 8~9만 바꾼 네 파일을 사용자가 실제 한글에서 비교했다.

| 파일 | 속성 UINT16 | bit 9 | bit 8 | 첫 번째 셀에서 관찰한 동작 |
| --- | --- | ---: | ---: | --- |
| s010-b010-c00.hwp | 0x0048 | 0 | 0 | 둘 다 직선 |
| s010-b010-c01.hwp | 0x0148 | 0 | 1 | Slash(`/`)만 꺾임 |
| s010-b010-c10.hwp | 0x0248 | 1 | 0 | BackSlash(`\`)만 꺾임 |
| s010-b010-c11.hwp | 0x0348 | 1 | 1 | 두 대각선 모두 꺾임 |

따라서 bit 8~9의 합성값 0/1/2/3은 이 조건에서 두 방향 꺾임 플래그의 조합이다. `3`이 미확인이라는 이전 중간 판단은 이 네 장의 캡처로 갱신한다. 두 비트를 하나의 boolean으로 줄이면 어느 방향이 꺾였는지 손실된다.

현재 모델은 다음처럼 분리한다.

```ts
slashCrooked: bit(properties, 8),
backSlashCrooked: bit(properties, 9),
backSlashCrookedSpec: bit(properties, 10),
```

bit 10은 명세에서 BackSlash 꺾은선으로 정의하므로 `backSlashCrookedSpec`으로 독립적으로 읽고 쓴다. bit 9와 OR로 합치거나, bit 9의 값을 bit 10에도 복제하지 않는다. **bit 10을 켰을 때의 실제 효과는 아직 확인하지 않았다.**

이 실험은 두 모양이 모두 `010`이고 중심선 bit 13이 꺼진 조건의 결과다. 중심선이 켜진 조합 등 다른 조건에서도 두 비트의 역할이 항상 같다고 일반화하지 않는다.

### E4. 대각선 모양 코드의 화면 관찰

아래 값은 파일 이름과 사용자가 제공한 캡처를 기준으로 한다. 대상은 항상 첫 행 첫 번째 셀이며 나머지 셀은 원본 그대로다.

| 파일 또는 조건 | 관찰 결과 | 해석 범위 |
| --- | --- | --- |
| s001-b000-c00.hwp | 대각선 표시 없음 | `001=1`은 명세에 의미가 열거되어 있지 않다. 이 조건에서 표시되지 않은 것을 확인했다. |
| s011-b000-c00.hwp | `/` 직선 표시 | 명세의 `011: LeftTop → BottomEdge` 설명과 세부 모양이 직접 대응하지 않는다. |
| s110-b000-c00.hwp | `/` 직선 표시 | `110=6`이 원본 샘플에 없다는 중간 한계를 갱신한다. 직접 설정한 사본에서 표시를 확인했다. |
| s010-b010-c00.hwp | `/`와 `\`가 교차하는 두 직선 | 두 모양 `010`이 함께 켜진 조건이다. |

`011`과 `110`은 모두 가운데 비트 `010`이 켜져 있다. 현재 환경이 가운데 비트만으로 기본 대각선을 그리고 나머지 비트의 세부 모양을 표시하지 않는다는 설명은 **가설**이다. 명세의 오류인지, 플랫폼 차이인지, 추가 조건이 필요한지는 확정하지 못했다.

표시가 같더라도 서로 다른 코드 2/3/6/7을 같은 값으로 정규화하지 않는다. 원시 3비트 값을 보존하며, 명세에 기재된 모양 설명과 실제 화면 관찰을 구분한다. 나머지 값·방향·회전 조합까지 전수 시각 검증한 것은 아니다.

### E5. 256개 조합 파일의 생성과 검증 범위

[대각선 샘플 HWP 원본](https://github.com/edwardkim/rhwp/blob/main/samples/%EB%8C%80%EA%B0%81%EC%84%A0%EC%83%98%ED%94%8C.hwp)을 복사해 다음 세 필드의 전체 비트 범위를 조합했다.

- Slash bit 2~4: 0~7.
- BackSlash bit 5~7: 0~7.
- 꺾임 bit 8~9: 0~3.
- 합계: `8 × 8 × 4 = 256`개.

원본 HWP 자체에서 다음을 확인했다.

- BodyText/Section0의 첫 번째 셀 LIST_HEADER는 `row=0`, `col=0`, BorderFill 참조 번호 `4`다.
- 대상은 DocInfo에서 네 번째로 등장하는 BorderFill이다. HWP BorderFill 페이로드에 별도 ID 필드가 있는 것이 아니다.
- 대상 레코드 헤더는 압축 해제된 DocInfo의 오프셋 994, 속성은 998~999에 있다.
- TABLE의 두 cellzone은 대상 셀에 겹치지 않는다.

각 파일에서 그 속성 2바이트 안의 bit 2~9만 변경했다. 256개를 다시 읽어 지정값, 레코드 경계, 다른 속성 비트, 나머지 8개 원본 스트림의 SHA-256 보존을 검사했다. 당시 파서에서 세 필드의 추출값도 256/256개가 일치했다. 이후 모델을 bit 8/9/10 각각의 boolean으로 분리하고, 여덟 조합의 읽기·쓰기 보존 테스트를 추가했다.

파일은 Slash·BackSlash가 모두 명세에 열거된 값 `0/2/3/6/7`인 100개와, 둘 중 하나라도 미정의 값 `1/4/5`인 156개로 나눴다. 이 분류는 모양 두 필드에 관한 것이며, 모든 조합의 시각적 의미가 명세에 정의됐다는 뜻은 아니다.

**256개 전체의 한글 화면 검증은 완료하지 않았다.** 화면 도구가 이미지 생성 오류, 이후 커널 파일 오류로 실행되지 않았다. E3·E4는 이후 사용자가 직접 열어 제공한 개별 캡처로 확인한 범위다. 바이너리 검사가 통과한 것을 한글의 표시 동작 검증으로 취급하지 않는다.

시험 파일의 내장 미리보기는 원본을 보존했다. 따라서 Finder 미리보기나 썸네일은 변경 후 결과가 아니며, 한글에서 본문을 직접 연 화면을 사용해야 한다.

### E6. 대각선 종류 바이트의 실제 의미 (2026-10-30)

사용자가 macOS 한글 12.30.0(6544)에서 직접 만든 파일을 프로젝트 파서로 읽어 확인했다.

| 조건 | 대각선 6B (종류, 굵기, 색) | 비고 |
| --- | --- | --- |
| 빈 문서 | `1, 0, #000000` | 대각선 모양 비트 `slashShape`·`backSlashShape`는 모두 0이다. |
| 1×1 표, 네 방향 빨간색 1mm 실선 | `1, 0, #000000` | 네 방향은 `1, 10, #BD3D3D`(실선, 1.0mm)로 읽혔다. 대각선은 지정하지 않았다. |
| 대각선 선 종류를 점선으로 지정 | 종류 `3` | `LineStyle.Dotted = 3`과 일치한다. |

대각선이 없는 파일에서도 종류가 `1`이므로, 표 27대로라면 대각선 없이 `BackSlash`가 기록된 셈이 된다. 반면 표 25 계열로 읽으면 `1=실선`, `3=점선`으로 두 관찰이 모두 설명된다. 프로젝트의 HWPX 픽스처 두 개도 대각선이 없는 BorderFill에 `<hh:diagonal type="SOLID" width="0.1 mm" color="#000000"/>`를 기록한다(HWP 동작의 확정 근거로는 쓰지 않는다). E1의 sample3.hwp 레코드처럼 종류 `0`이 기록된 경우는 `0=선 없음`으로 읽힌다.

이에 따라 HWP 라이터는 대각선 정보가 없을 때 한글 빈 문서와 같은 `1, 0, #000000`을 기록한다. 종류 `0`과 `2` 이상 중 `3`을 제외한 값은 한글에서 개별 설정해 비교하지 않았다.

## 2026-10-30 실험 기록: 채우기 정보 (표 28)

환경은 macOS용 한컴오피스 한글 12.30.0(6544)이다. 실험 파일, 기반 파일, 재현 명령은 `experiments/`의 각 폴더에 있다. 여기에는 결론과 판단 범위만 적는다.

### E7. 그러데이션 필드 크기 (`experiments/fill-gradient-field-sizes`)

같은 그러데이션 값을 명세의 `INT16 × 6` 배치와 `UINT8 + INT32 × 5` 배치로 넣었다. 뒤 배치는 속성 창에 값이 그대로 보였고, 명세 배치는 엉뚱한 값(시작·끝 색 검정, 중심 100/0, 기울임 359)으로 읽혔다. 이후 한글에서 그러데이션을 직접 지정해 저장한 레코드도 뒤 배치였다.

색 수가 2보다 클 때의 위치 배열은 확인하지 못했다. macOS 한글은 그러데이션 색을 2개까지만 설정할 수 있다.

### E8. 번짐 정도 (`experiments/fill-gradient-step-zero`)

번짐 정도만 `0`, `50`, `255`로 바꿨다. `0`은 속성 창 값이 정상인데 셀이 칠해지지 않았고, `50`과 `255`는 칠해졌다. 한글이 저장한 그러데이션에도 `255`가 있었으므로 명세의 `0 -100` 범위는 실제와 다르다.

### E9. 채우기 정보의 꼬리와 그림 정보

한글이 직접 저장한 레코드의 채우기 부분이다.

```text
채우기 없음  00 00 00 00 | 00 00 00 00
단색         01 00 00 00 | (단색 12B)            | 00 00 00 00 | 00
이미지       02 00 00 00 | 0f 4b 32 00 01 00     | 00 00 00 00 | 00
그러데이션   04 00 00 00 | (그러데이션 29B)      | 01 00 00 00 | 32 | 00
```

- 추가 채우기 속성 길이 `DWORD`는 모든 경우에 하나만 있다. 그러데이션일 때만 `1`이고 번짐 중심 1B가 따라온다. 명세의 네 행은 이 두 필드를 두 번 적은 것이다(정정 8, 9).
- 채우기가 있으면 마지막에 1B가 더 있고, 모두 `00`이었다(정정 10).
- 이미지 행은 유형 `0f`(원래 크기에 비례하여), 명암 `4b`(75), 밝기 `32`(50), 효과 `00`, BinItem ID `01 00`이다. 한글에서 밝기 50, 명암 75로 지정했으므로 명암이 먼저다(정정 11).
- 그림 효과 값은 `0`만 봤고, 명암·밝기의 음수는 확인하지 않았다.

### E10. 마지막 1바이트 (`experiments/fill-trailing-unknown-byte`)

이미지 채우기 파일에서 마지막 1B만 `50`, `128`, `255`로 바꿨다. 셋 다 원본과 표시가 같았다. 한글에는 셀 채우기 투명도 설정도 없다. rhwp 정오표 8번은 이를 투명도로 보지만, 이 환경에서는 표시에 영향이 없으므로 의미를 확정하지 않는다.

### E11. 여러 채우기 종류 (`experiments/fill-multi-kind-priority`)

한글 UI는 채우기를 하나만 고르게 하고, 저장할 때도 하나만 남긴다. 다른 종류로 바꿔 저장하면 이전 블록이 지워지고, 그림에서 다른 종류로 바꾸면 BinData의 그림도 지워진다.

여러 비트를 켠 파일(종류 3, 5, 6, 7)도 오류 없이 열렸고, 결과는 3→이미지, 5→그러데이션, 6→이미지, 7→이미지였다. 즉 **이미지 > 그러데이션 > 단색**이다. 블록은 단색, 그러데이션, 이미지 순으로 넣었고, 마지막 1B는 켜진 종류마다 하나씩 넣었다(rhwp 기준). 일곱 파일이 모두 정상으로 열렸으므로 이 배치는 한글과 어긋나지 않는다. 다만 한글이 직접 저장한 복수 종류 파일은 없으므로, 마지막 1B가 종류마다 붙는다는 것은 확정이 아니다.

결과가 본문에 그려진 모습인지 속성 창 값인지는 구분해 기록하지 않았다.

## 2026-11-11~12 실험 기록: 문단 번호 (표 38~41)

E14의 환경은 macOS용 한컴오피스 한글 12.30.0(6544)이다. 실험 파일은 `experiments/numbering-format-bits`, `numbering-format-high-bits`, `numbering-align-out-of-range`, `numbering-distance-kind`, `numbering-extended-levels`, `numbering-start-number-source`에 있다. 한글의 표시 동작은 `hangul-behavior.md`의 "문단 번호 모양"에 적었다.

### E14. 문단 머리 정보와 속성 비트

**레코드 구조**: 저장소의 HWP 파일에서 `HWPTAG_NUMBERING` 63개를 직접 읽었다. 모두 수준마다 머리 정보 12B, 번호 형식 길이, 번호 형식 문자열 순으로 7회 읽혔고, 문자열이 `^1.`부터 `^7`까지 수준 순서와 맞았다(정정 25, 26). 한 레코드는 230B였고, 7개 수준과 시작 번호 UINT16까지 읽으면 144B다. 나머지 86B(수준별 시작번호, 확장 수준 8~10)는 E15에서 확인했다.

**속성 비트**: 한글 기본 개요 번호(`1. / 가. / 1) / 가) / (1) / (가) / ①`)의 1, 2, 7수준 속성은 `0x0C`, `0x10C`, `0x2C`였다. bit 5부터 읽으면 0, 8, 1로 표 41의 1,2,3 / 가,나,다 / ①②③과 맞는다. 이후 한글에서 설정을 바꿔 저장하고 바이트와 설정 창을 비교했다.

| 설정 창 | 저장된 값 |
| --- | --- |
| 번호 모양 ㊀㊁㊂ | 속성 `0x1CC`, bit 5~9 = 14 |
| 정렬 오른쪽 | bit 0~1 = 2 |
| 번호 너비를 자릿수에 맞춤 끔 | bit 2 = 0 |
| 자동으로 내어쓰기 끔 | bit 3 = 0 |
| 너비 조정 20.0 mm | 너비 보정값 5669 (HWPUNIT) |
| 본문과의 간격 50 % | bit 4 = 0, 거리 50 |
| 본문과의 간격 10 mm | bit 4 = 1, 거리 2834. 다시 열면 28.3 pt로 표시 |
| 글자 모양 지정 켬 | 글자 모양 아이디 7. 끈 수준은 `0xFFFFFFFF` |

속성 비트를 직접 바꾼 사본도 열었다.

- bit 5~9를 16으로 바꾸자 甲, 乙, 丙으로 표시됐다(정정 27, 28).
- bit 4만 켜고 거리를 70으로 두자 본문과의 간격이 0.7 pt로 표시됐다(정정 29).
- bit 10~31을 켠 결과와 범위 밖 값(번호 형식 17 이상, 정렬 3)의 처리는 `hangul-behavior.md`에 있다. bit 10 이상의 의미는 확인하지 못했다.

### E15. 수준별 시작번호와 확장 수준 8~10 (`experiments/numbering-extended-levels`)

환경은 macOS 한글이다. 앱 버전은 기록하지 않았다.

**레코드 구조**: 저장소와 옆 프로젝트 `rhwp`, `hwp-test`의 HWP 72개에서 `HWPTAG_NUMBERING` 88개를 읽었다. 다음 구조로 88개 모두 레코드 끝에서 정확히 끝났다.

| 버전 | 레코드 수 | 구조 |
| --- | ---: | --- |
| 5.1.1.0 | 63 | 1~7수준, 시작 번호 UINT16, 수준별 시작번호 UINT32 × 7, 8~10수준, 확장 수준별 시작번호 UINT32 × 3 |
| 5.1.0.1 | 22 | 위와 같다 |
| 5.0.3.0 | 3 | 수준별 시작번호 UINT32 × 7에서 끝난다 |

버전 조건(5.0.2.5 이상, 5.1.0.0 이상)은 명세와 맞는다. 5.0.2.5 미만 파일은 없었다. 8~10수준에도 12B 머리 정보가 있었고(정정 30), 확장 시작번호 3개는 세 수준이 다 끝난 뒤 이어졌다. 한글 기본값은 8~10수준 속성 `0x12C`, `0x14C`, `0x6C`(번호 형식 9, 10, 3), 형식 문자열 `^8`, 빈 문자열, 빈 문자열이었다.

**시작번호의 자리**: 한글에서 1·2·9수준의 시작 번호를 52, 5, 7로 바꿔 저장하자 수준별 시작번호의 첫째, 둘째 자리와 확장 시작번호의 둘째 자리에 각각 저장됐다. 명세의 반복 순서와 맞는다. 3~8, 10수준은 값을 바꿔 확인하지 않았다.

**확장 수준의 표시**: 9수준을 번호 형식 3, 형식 `^9..`로 두자 본문에 "i.."로 표시됐다. 10수준 형식에 `^10`을 넣자 1수준 번호 뒤에 `0`이 붙어 "520"으로 표시됐고, `^1가.^9`는 "52가.i"로 표시됐다(정정 32).

**문단 모양**: 9·10수준 문단이 쓰는 문단 모양 레코드는 58B였고, 끝 UINT32(오프셋 54)에 8, 9가 있었다. 속성1 bit 25~27은 둘 다 6이었다. 문단 모양(표 43)은 아직 대조하지 않았으므로 정오표에 넣지 않고 `BACKLOG.md`에 남긴다.

### E16. 시작 번호 UINT16 (`experiments/numbering-start-number-source`)

한글에서 1수준 시작 번호를 바꾸면 UINT16도 같은 값으로 저장됐다(52, 23). 1수준 시작번호 UINT32는 23으로 두고 UINT16만 99로 바꾼 사본을 열자 1수준 번호가 23으로 표시됐다. 같은 파일의 기본 번호 레코드는 UINT16이 0, 1수준 시작번호가 1이라 늘 같은 값도 아니다(정정 33).

## 2026-11-14 실험 기록: 글머리표 (표 42)

### E17. 이미지 글머리표 (`experiments/bullet-image-id`)

환경은 macOS 한글이다. 앱 버전은 기록하지 않았다. 파일 버전은 5.1.1.0이다. 레코드는 `scripts/dump-bullets.ts`로 출력했다.

**레코드 구조**: 저장소와 옆 프로젝트 `rhwp`, `hwp-test`의 HWP 72개 중 글머리표 레코드가 있는 파일은 `hwp-test/src/fixtures/sample3.hwp` 하나였다(28개, 모두 이미지 없음). 여기에 실험 기반 파일의 2개(모두 이미지)를 더한 30개가 모두 25B였다. 문단 머리 정보 12B, 글머리표 문자 2B, 이미지 여부 4B, 이미지 정보 5B, 체크 글머리표 문자 2B로 읽으면 레코드 끝에서 정확히 끝난다(정정 34, 35).

| 오프셋 | 길이 | 내용 |
| ---: | ---: | --- |
| 0 | 12 | 문단 머리 정보. 30개 모두 글자 모양 아이디가 `0xFFFFFFFF` |
| 12 | 2 | 글머리표 문자 |
| 14 | 4 | 이미지 여부. 0 또는 1 |
| 18 | 3 | 이미지 정보 1B × 3. 실물에서 모두 0 |
| 21 | 2 | BinData ID `UINT16`. 이미지가 없으면 0 |
| 23 | 2 | 체크 글머리표 문자 |

**이미지 여부와 ID**: 기반 파일 `base.hwp`는 한글에서 이미지 글머리표 두 개를 적용해 저장했다. BinData는 BIN0001.png, BIN0002.png, BIN0003.jpg이고, 두 레코드의 오프셋 21~22는 `03 00`, `01 00`, 이미지 여부는 둘 다 1이었다(정정 36). ID는 BinData 레코드의 ID 필드, 스트림 이름 번호와 같다.

**ID의 폭**: 첫째 레코드의 오프셋 22만 `00`에서 `01`로 바꾼 `id-0x0103.hwp`(`scripts/patch-bullet-image-id.ts`)를 열자 그 글머리표의 그림이 표시되지 않았다. 사용자가 이 파일을 한글에서 다시 저장한 `id-0x0103-resaved.hwp`에서는 다음이 바뀌었다.

- 오프셋 21~22가 `00 00`이 됐다. 이미지 여부는 1로 남았다.
- BIN0003.jpg 스트림과 그 BinData 레코드가 없어졌다.

`03`을 ID 3으로 읽었다면 BIN0003은 쓰이는 데이터로 남았을 것이다. 그래서 ID를 `UINT16`(0x0103 = 259)으로 본다(정정 37). 오프셋 22가 0이어야 하는 예약 바이트이고, 0이 아니면 한글이 이미지 전체를 무효로 보는 경우도 같은 결과를 낸다. ID 256 이상의 실물이 없어 이 가능성은 배제하지 못했다.

**체크 글머리표 문자**: 30개 중 U+0000이 11개, U+0020이 15개, U+F0A4가 4개였다. U+F0A4는 `sample3.hwp`에서만 나왔다. 이 값의 뜻과 한글에서 설정하는 방법은 확인하지 않았다(정정 38).

**확인하지 않은 것**

- 이미지 정보 1B 세 개의 순서(명세는 대비, 밝기, 효과). 실물에서 모두 0이었다.
- 이미지 여부 1, ID 0인 레코드(`id-0x0103-resaved.hwp`)를 한글이 어떻게 표시하는지.

## 2026-11-14 실험 기록: 문단 모양 (표 43)

### E18. 여백, 문단 간격, 테두리 간격의 단위

환경과 앱 버전은 기록하지 않았다. 한글 문단 모양 창에서 값을 넣고 hwp-watch로 레코드를 봤다.

| 필드 | 설정 | 저장 값 |
| --- | --- | ---: |
| 왼쪽 여백 | 25pt | 5000 |
| 왼쪽 여백 | -10pt | -2000 |
| 왼쪽 여백 | 0.1pt | 20 |
| 첫 줄 들여쓰기 | 10pt | 2000 |
| 첫 줄 내어쓰기 | 10pt | -2000 |

오른쪽 여백, 문단 간격 위·아래도 HWPUNIT(1pt = 100)의 2배였다(정정 39). 한글 UI는 0.1pt보다 작은 값을 받지 않아서 pt로 넣으면 저장 값은 늘 20의 배수다.

Windows용 한글 문단 모양 창의 입력 범위는 왼쪽·오른쪽 여백 -415.0~415.0pt(저장 값 ±83000), 문단 간격 위·아래 0~841.8pt(저장 값 0~168360)다.

문단 테두리 간격(테두리 탭의 간격, 오프셋 34~41)은 네 방향 모두 HWPUNIT 그대로였다. 1pt를 넣자 100이 저장됐다(정정 40). Windows용 한글의 테두리 탭은 0~25mm, 0~70.8pt만 받는다.

**확인하지 않은 것**

- 저장 값이 홀수인 경우. mm 등 다른 단위로 넣었을 때 생기는지, 파일에 홀수를 넣으면 한글이 어떻게 표시하는지.

### Windows에서 후속 확인할 사항

- bit 10만 켜고 끄면서, bit 8/9와 독립적인 효과가 있는지 확인한다.
- Slash·BackSlash 모양 `000/010/011/110/111`을 각각 고정된 조건에서 비교한다. 특히 macOS에서 같아 보인 `011`과 `110`의 차이를 확인한다.
- 중심선 bit 13, 회전 bit 11/12를 각각 켠 조건에서도 꺾임 bit 8/9의 역할을 확인한다.
- 일반 선 종류 14~17의 3D 계열이 표시되는 조건과 값별 모양을 확인한다.
- 대각선 선 종류를 점선 이외의 값(특히 `0`, `2`)으로 바꿔 E6의 대응을 확인한다.
- 그러데이션 색을 3개 이상 지정해, 위치 배열(`INT32 × num`)의 배치를 확인한다(E7).
