## 2026-10-28 실험 기록

이 절은 실제 바이트 검사, 한글 화면에서의 관찰, 미확인 사항을 구분한다. 명세와 다른 표시가 나왔다는 이유만으로 명세의 모든 설명이 잘못됐다고 단정하지 않는다.

- 에이전트가 직접 화면을 확인한 환경: macOS 한글 `12.30.0`, 빌드 `6313`, 읽기 전용 모드.
- 대각선의 개별 조합은 사용자가 실제 한글에서 연 뒤 제공한 캡처로 확인했다. 그 캡처의 앱 버전은 별도로 확인하지 않았다.
- Windows 한글에서의 비교는 별도 후속 작업이다. 아래 macOS 관찰을 Windows의 동작으로 일반화하지 않는다.
- 이 기록에서 HWPX는 HWP 동작을 확정하는 기준으로 사용하지 않는다.

### E1. BorderFill의 실제 바이트 배치

기존 HWP 파일을 CFB 라이브러리로 열고, FileHeader의 압축 플래그에 따라 DocInfo를 압축 해제한 뒤 레코드 헤더와 페이로드를 직접 검사했다. 프로젝트의 HWP 라이터가 만든 파일로 배치를 증명하지 않았다.

| 원본 파일 | BorderFill 레코드 수 |
| --- | ---: |
| sample.hwp | 2 |
| sample2.hwp | 18 |
| sample3.hwp | 574 |
| sample4.hwp | 36 |
| 합계 | 630 |

검사한 레코드는 모두 아래 32바이트 구간을 포함했다. 나머지 바이트에는 채우기 정보 등이 이어진다. 오프셋은 레코드 헤더를 제외한 페이로드 시작 기준이다.

| 오프셋 | 내용 |
| --- | --- |
| 0~1 | 속성 UINT16 |
| 2~7 | 왼쪽: 종류 1B + 굵기 1B + 색상 4B |
| 8~13 | 오른쪽: 같은 6B 구성 |
| 14~19 | 위쪽: 같은 6B 구성 |
| 20~25 | 아래쪽: 같은 6B 구성 |
| 26~31 | 대각선: 종류 1B + 굵기 1B + 색상 4B |

예를 들어 sample3.hwp의 한 레코드는 다음처럼 읽힌다.

```text
00 00                 속성
00 00 FF FF FF FF     왼쪽
00 00 FF FF FF FF     오른쪽
01 00 5B 9B D5 00     위쪽
01 00 5B 9B D5 00     아래쪽
00 00 FF FF FF FF     대각선
```

일반 테두리 네 방향과 대각선은 바이트 길이와 종류 값의 타입이 같다. 대각선도 `BorderLine`(종류는 `LineStyle`)으로 모델링한다. 명세 표 27의 `0=Slash`, `1=BackSlash`, `2=CrookedSlash` 해석은 E6에서 실제 값과 맞지 않는 것을 확인했다.

현재 읽기 구현은 네 방향을 종류·굵기·색상 한 세트씩 읽고, 대각선은 `hasMore(6)`일 때 읽는다. 이는 현재 파서의 처리 정책이며, 잘린 대각선 레코드가 정상이라는 실험 결과는 아니다.

### E2. 일반 테두리선 종류 값

정상적으로 열리는 sample.hwp를 기준으로, 네 방향 선 종류를 0~17로 바꾼 사본 18개를 실제 한글에서 열었다. 굵기와 색상은 동일하게 고정했다. 각 사본의 종류 바이트가 의도한 값인지와 DocInfo 이외의 원본 스트림 보존을 확인했다.

| 실제 값 | 관찰한 표시 또는 추정 이름 | 판정 |
| ---: | --- | --- |
| 0 | 선 없음 | 화면 확인 |
| 1 | 실선 | 화면 확인 |
| 2 | 긴 점선 | 화면 확인 |
| 3 | 점선 | 화면 확인 |
| 4 | 일점쇄선 | 화면 확인 |
| 5 | 이점쇄선 | 화면 확인 |
| 6 | 더 긴 선분의 반복 | 화면 확인 |
| 7 | 원형 점의 반복 | 화면 확인 |
| 8 | 이중선 | 화면 확인 |
| 9 | 가는선 + 굵은선 이중선 | 화면 확인 |
| 10 | 굵은선 + 가는선 이중선 | 화면 확인 |
| 11 | 가는선 + 굵은선 + 가는선 삼중선 | 화면 확인 |
| 12 | 물결 | 화면 확인 |
| 13 | 물결 이중선 | 화면 확인 |
| 14 | 두꺼운 3D | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
| 15 | 두꺼운 3D, 광원 반대 | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
| 16 | 3D 단선 | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |
| 17 | 3D 단선, 광원 반대 | 이름 대응은 추정. 현재 환경에서는 선이 표시되지 않음 |

14~17은 속성 bit 0의 3D 효과를 켠 사본 4개도 비교했지만 선이 표시되지 않았다. 이 결과만으로 값이 무효이거나 의미가 없다고 결론 내리지 않는다. 추가 속성이나 한글 버전·플랫폼에 따른 표시 조건은 미확인이다.

명세의 실선 이후 항목이 실제 값보다 1 작게 적힌 것은 `선 없음=0` 항목 누락에 따른 차이로 추정한다. 0~13은 관찰로 뒷받침되지만, 3D 계열 전체의 대응까지 시각적으로 확정한 것은 아니다.

시험 중 DocumentBuilder로 새로 생성한 별도 문서는 한글에서 파일 손상 경고가 나왔다. 그 문서는 위 결과에서 제외하고 정상 원본의 바이너리를 직접 변경한 사본으로 검증했다. 생성 문서의 손상 원인은 이번 실험 범위에서 조사하지 않았다.

### E3. bit 8과 bit 9의 독립적인 꺾임 플래그

대각선 샘플 HWP의 첫 행 첫 번째 셀을 대상으로, Slash 모양과 BackSlash 모양을 모두 `010`으로 고정했다. bit 10과 나머지 속성은 고정한 채 bit 8~9만 바꾼 네 파일을 사용자가 실제 한글에서 비교했다.

| 파일 | 속성 UINT16 | bit 9 | bit 8 | 첫 번째 셀에서 관찰한 동작 |
| --- | --- | ---: | ---: | --- |
| s010-b010-c00.hwp | 0x0048 | 0 | 0 | 둘 다 직선 |
| s010-b010-c01.hwp | 0x0148 | 0 | 1 | Slash(`/`)만 꺾임 |
| s010-b010-c10.hwp | 0x0248 | 1 | 0 | BackSlash(`\`)만 꺾임 |
| s010-b010-c11.hwp | 0x0348 | 1 | 1 | 두 대각선 모두 꺾임 |

따라서 bit 8~9의 합성값 0/1/2/3은 이 조건에서 두 방향 꺾임 플래그의 조합이다. `3`이 미확인이라는 이전 중간 판단은 이 네 장의 캡처로 갱신한다. 두 비트를 하나의 boolean으로 줄이면 어느 방향이 꺾였는지 손실된다.

현재 모델은 다음처럼 분리한다.

```ts
slashCrooked: bit(properties, 8),
backSlashCrooked: bit(properties, 9),
backSlashCrookedSpec: bit(properties, 10),
```

bit 10은 명세에서 BackSlash 꺾은선으로 정의하므로 `backSlashCrookedSpec`으로 독립적으로 읽고 쓴다. bit 9와 OR로 합치거나, bit 9의 값을 bit 10에도 복제하지 않는다. **bit 10을 켰을 때의 실제 효과는 아직 확인하지 않았다.**

이 실험은 두 모양이 모두 `010`이고 중심선 bit 13이 꺼진 조건의 결과다. 중심선이 켜진 조합 등 다른 조건에서도 두 비트의 역할이 항상 같다고 일반화하지 않는다.

### E4. 대각선 모양 코드의 화면 관찰

아래 값은 파일 이름과 사용자가 제공한 캡처를 기준으로 한다. 대상은 항상 첫 행 첫 번째 셀이며 나머지 셀은 원본 그대로다.

| 파일 또는 조건 | 관찰 결과 | 해석 범위 |
| --- | --- | --- |
| s001-b000-c00.hwp | 대각선 표시 없음 | `001=1`은 명세에 의미가 열거되어 있지 않다. 이 조건에서 표시되지 않은 것을 확인했다. |
| s011-b000-c00.hwp | `/` 직선 표시 | 명세의 `011: LeftTop → BottomEdge` 설명과 세부 모양이 직접 대응하지 않는다. |
| s110-b000-c00.hwp | `/` 직선 표시 | `110=6`이 원본 샘플에 없다는 중간 한계를 갱신한다. 직접 설정한 사본에서 표시를 확인했다. |
| s010-b010-c00.hwp | `/`와 `\`가 교차하는 두 직선 | 두 모양 `010`이 함께 켜진 조건이다. |

`011`과 `110`은 모두 가운데 비트 `010`이 켜져 있다. 현재 환경이 가운데 비트만으로 기본 대각선을 그리고 나머지 비트의 세부 모양을 표시하지 않는다는 설명은 **가설**이다. 명세의 오류인지, 플랫폼 차이인지, 추가 조건이 필요한지는 확정하지 못했다.

표시가 같더라도 서로 다른 코드 2/3/6/7을 같은 값으로 정규화하지 않는다. 원시 3비트 값을 보존하며, 명세에 기재된 모양 설명과 실제 화면 관찰을 구분한다. 나머지 값·방향·회전 조합까지 전수 시각 검증한 것은 아니다.

### E5. 256개 조합 파일의 생성과 검증 범위

[대각선 샘플 HWP 원본](https://github.com/edwardkim/rhwp/blob/main/samples/%EB%8C%80%EA%B0%81%EC%84%A0%EC%83%98%ED%94%8C.hwp)을 복사해 다음 세 필드의 전체 비트 범위를 조합했다.

- Slash bit 2~4: 0~7.
- BackSlash bit 5~7: 0~7.
- 꺾임 bit 8~9: 0~3.
- 합계: `8 × 8 × 4 = 256`개.

원본 HWP 자체에서 다음을 확인했다.

- BodyText/Section0의 첫 번째 셀 LIST_HEADER는 `row=0`, `col=0`, BorderFill 참조 번호 `4`다.
- 대상은 DocInfo에서 네 번째로 등장하는 BorderFill이다. HWP BorderFill 페이로드에 별도 ID 필드가 있는 것이 아니다.
- 대상 레코드 헤더는 압축 해제된 DocInfo의 오프셋 994, 속성은 998~999에 있다.
- TABLE의 두 cellzone은 대상 셀에 겹치지 않는다.

각 파일에서 그 속성 2바이트 안의 bit 2~9만 변경했다. 256개를 다시 읽어 지정값, 레코드 경계, 다른 속성 비트, 나머지 8개 원본 스트림의 SHA-256 보존을 검사했다. 당시 파서에서 세 필드의 추출값도 256/256개가 일치했다. 이후 모델을 bit 8/9/10 각각의 boolean으로 분리하고, 여덟 조합의 읽기·쓰기 보존 테스트를 추가했다.

파일은 Slash·BackSlash가 모두 명세에 열거된 값 `0/2/3/6/7`인 100개와, 둘 중 하나라도 미정의 값 `1/4/5`인 156개로 나눴다. 이 분류는 모양 두 필드에 관한 것이며, 모든 조합의 시각적 의미가 명세에 정의됐다는 뜻은 아니다.

**256개 전체의 한글 화면 검증은 완료하지 않았다.** 화면 도구가 이미지 생성 오류, 이후 커널 파일 오류로 실행되지 않았다. E3·E4는 이후 사용자가 직접 열어 제공한 개별 캡처로 확인한 범위다. 바이너리 검사가 통과한 것을 한글의 표시 동작 검증으로 취급하지 않는다.

시험 파일의 내장 미리보기는 원본을 보존했다. 따라서 Finder 미리보기나 썸네일은 변경 후 결과가 아니며, 한글에서 본문을 직접 연 화면을 사용해야 한다.

### E6. 대각선 종류 바이트의 실제 의미 (2026-10-30)

사용자가 macOS 한글에서 직접 만든 파일을 프로젝트 파서로 읽어 확인했다. 앱 버전은 별도로 확인하지 않았다.

| 조건 | 대각선 6B (종류, 굵기, 색) | 비고 |
| --- | --- | --- |
| 빈 문서 | `1, 0, #000000` | 대각선 모양 비트 `slashShape`·`backSlashShape`는 모두 0이다. |
| 1×1 표, 네 방향 빨간색 1mm 실선 | `1, 0, #000000` | 네 방향은 `1, 10, #BD3D3D`(실선, 1.0mm)로 읽혔다. 대각선은 지정하지 않았다. |
| 대각선 선 종류를 점선으로 지정 | 종류 `3` | `LineStyle.Dotted = 3`과 일치한다. |

대각선이 없는 파일에서도 종류가 `1`이므로, 표 27대로라면 대각선 없이 `BackSlash`가 기록된 셈이 된다. 반면 표 25 계열로 읽으면 `1=실선`, `3=점선`으로 두 관찰이 모두 설명된다. 프로젝트의 HWPX 픽스처 두 개도 대각선이 없는 BorderFill에 `<hh:diagonal type="SOLID" width="0.1 mm" color="#000000"/>`를 기록한다(HWP 동작의 확정 근거로는 쓰지 않는다). E1의 sample3.hwp 레코드처럼 종류 `0`이 기록된 경우는 `0=선 없음`으로 읽힌다.

이에 따라 HWP 라이터는 대각선 정보가 없을 때 한글 빈 문서와 같은 `1, 0, #000000`을 기록한다. 종류 `0`과 `2` 이상 중 `3`을 제외한 값은 한글에서 개별 설정해 비교하지 않았다.

### Windows에서 후속 확인할 사항

- bit 10만 켜고 끄면서, bit 8/9와 독립적인 효과가 있는지 확인한다.
- Slash·BackSlash 모양 `000/010/011/110/111`을 각각 고정된 조건에서 비교한다. 특히 macOS에서 같아 보인 `011`과 `110`의 차이를 확인한다.
- 중심선 bit 13, 회전 bit 11/12를 각각 켠 조건에서도 꺾임 bit 8/9의 역할을 확인한다.
- 일반 선 종류 14~17의 3D 계열이 표시되는 조건과 값별 모양을 확인한다.
- 대각선 선 종류를 점선 이외의 값(특히 `0`, `2`)으로 바꿔 E6의 대응을 확인한다.
