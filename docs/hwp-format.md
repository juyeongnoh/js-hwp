## 1. 한글 파일 구조 요약

HWP 파일은 CFB(Compound File Binary) 구조를 가진다. 내부적으로 폴더의 역할을 하는 스토리지, 파일의 역할을 하는 스트림을 가진다.

> 📂 = 스토리지<br/>📄 = 스트림

**[표 2] 파일 전체 구조**

| 설명            | 구별 이름                                                               | 길이(바이트) | 레코드 구조 | 압축/암호화 |
| --------------- | ----------------------------------------------------------------------- | ------------ | ----------- | ----------- |
| 파일 인식 정보  | 📄 FileHeader                                                           | 고정         |             |             |
| 문서 정보       | 📄 DocInfo                                                              | 가변\*       | ✅          | ✅          |
| 본문            | 📂 BodyText<br/>├ 📄 Section0<br/>├ 📄 Section1<br/>└ 📄 ...            | 가변         | ✅          | ✅          |
| 문서 요약       | 📄 \005HwpSummaryInformation                                            | 고정         |             |             |
| 바이너리 데이터 | 📂 BinData<br/>├ 📄 **BIN0001.jpg**<br/>├ 📄 **BIN0002.png**<br/>└ 📄 ...       | 가변         |             | ✅          |
| 미리보기 텍스트 | 📄 PrvText                                                              | 고정         |             |             |
| 미리보기 이미지 | 📄 PrvImage                                                             | 가변         |             |             |
| 문서 옵션       | 📂 DocOptions<br/>├ 📄 \_LinkDoc<br/>├ 📄 DrmLicense<br/>└ 📄 ...       | 가변         |             |             |
| 스크립트        | 📂 Scripts<br/>├ 📄 DefaultJScript<br/>├ 📄 JScriptVersion<br/>└ 📄 ... | 가변         |             |             |
| XML 템플릿      | 📂 XMLTemplate<br/>├ 📄 Schema<br/>├ 📄 Instance<br/>└ 📄 ...           | 가변         |             |             |
| 문서 이력 관리  | 📂 DocHistory<br/>├ 📄 VersionLog0<br/>├ 📄 VersionLog1<br/>└ 📄 ...    | 가변         | ✅          | ✅          |

\* 공식 명세의 표 2는 `DocInfo` 길이를 “고정”으로 표시하지만, 같은 명세의 표 4는 `HWPTAG_FACE_NAME` 등 개별 레코드와 `DocInfo`의 전체 길이를 “가변”으로 표시한다. 이 표의 길이는 실제 스트림의 바이트 수를 뜻하므로 `가변`으로 바로잡았다.

### COLORREF

파일에 R, G, B, 최상위 바이트 순서로 저장된다(4B). **최상위 바이트는 0이 아닐 수 있다.** 의미는 모른다. 셀 배경에서 `FF FF FF FF`는 색 없음, `FF FF FF 00`은 흰색이다. 다른 필드와 다른 값은 확인하지 않았다.

### 바이너리 데이터

**[표 17] 바이너리 데이터**

| 자료형      | 길이(바이트) | 설명                                                         |
| ----------- | ------------ | ------------------------------------------------------------ |
| UINT16      | 2            | 속성(표 18)                                                  |

\* 비트 플래그지만 한글은 하나만 저장한다. 여러 비트가 켜진 파일은 오류 없이 열고, 이미지 > 그러데이션 > 단색 순으로 하나만 쓴다. 블록은 단색, 그러데이션, 이미지 순으로 이어진다.

\*\* 미확인. 위치 배열은 3색 이상 그러데이션이 필요한데 macOS 한글은 2색까지만 설정할 수 있다. 그림 효과는 0만 확인했다. 명암·밝기의 음수도 확인하지 않았다.

\*\*\* 채우기가 있으면 1바이트가 붙고, 채우기 없음에는 없다. 한글이 저장한 파일에서는 모두 `0`이었고, 값을 `50`, `128`, `255`로 바꿔도 표시가 같았다. rhwp는 투명도로 해석하지만 한글에는 셀 채우기 투명도 설정이 없다. 켜진 종류마다 1바이트라는 것은 rhwp 기준이고, 한글이 직접 저장한 복수 종류 파일이 없어 확정하지 않았다.

명세 표 28은 공통 꼬리를 이미지 채우기 구획 아래에 `DWORD`·`BYTE`·`DWORD`·`BYTE[size]` 네 행으로 적는다. 실제로는 위 표의 `DWORD`와 `BYTE[size]` 두 필드뿐이고, 명세는 같은 필드를 두 번 적었다. 명세의 둘째 조건식 `type & 0x0000001`은 `0x0000004`의 오타다.

**한글이 저장한 채우기 부분**

```text
채우기 없음  00 00 00 00 | 00 00 00 00
단색         01 00 00 00 | ff ff ff ff 99 99 99 00 ff ff ff ff | 00 00 00 00 | 00
이미지       02 00 00 00 | 0f 4b 32 00 01 00                   | 00 00 00 00 | 00
그러데이션   04 00 00 00 | (아래)                              | 01 00 00 00 | 32 | 00
```

그러데이션: 빨강→파랑, 기울임 90, 가로·세로 중심 0, 번짐 정도 255, 번짐 중심 50.

```text
04 00 00 00     채우기 종류: 그러데이션
01              유형
5a 00 00 00     기울임 90
00 00 00 00     가로 중심 0
00 00 00 00     세로 중심 0
ff 00 00 00     번짐 정도 255
02 00 00 00     색 수 2
ff 00 00 00     빨강
00 00 ff 00     파랑
01 00 00 00     추가 채우기 속성 길이 1
32              번짐 중심 50
00              알 수 없음
```

|             |              | **위 세 필드가 수준 8~10에 대해 3회 반복**                  |
| UINT32 × 3  | 12           | 확장 수준별 시작번호, 수준 8~10 순서 (5.1.0.0 이상)         |
| 전체 길이   | 가변         | **(14 + 2×len) × 7 + 2 + 28 + (14 + 2×len) × 3 + 12**       |

버전 조건은 레코드에 남은 길이로 판단한다. 5.0.3.0 레코드는 수준별 시작번호에서 끝났다.

\* 한글은 1수준 번호를 표시할 때 수준별 시작번호의 첫 값을 쓴다. 1수준 시작 번호를 바꾸면 이 값도 같이 저장되지만, 기본 번호 레코드에서는 0으로 1수준 값(1)과 달랐다. 뜻은 모른다.

번호 형식의 수준 번호는 `^` 뒤 한 글자로 넣고 `^1`~`^9`까지다. 10수준 번호를 넣는 코드는 찾지 못했다(`^10`은 `^1` 뒤의 글자 `0`).

**[표 39] 문단 머리 정보**

| 자료형    | 길이(바이트) | 설명                                                    |
| --------- | ------------ | ------------------------------------------------------- |
| UINT32    | 4            | 속성(표 40)                                             |
| HWPUNIT16 | 2            | 너비 보정값. **HWPUNIT**                                |
| HWPUNIT16 | 2            | 본문과의 거리. bit 4에 따라 % 또는 **HWPUNIT**          |
| UINT32    | 4            | 글자 모양 아이디. 지정하지 않으면 `0xFFFFFFFF`          |
| 전체 길이 | **12**       |                                                         |

화면에서 고른 단위(mm, pt 등)는 저장되지 않는다.

**[표 40] 문단 머리 정보 속성**

| 비트      | 설명                                                                 |
| --------- | -------------------------------------------------------------------- |
| bit 0~1   | 정렬. 0 왼쪽, 1 가운데, 2 오른쪽                                     |
| bit 2     | 번호 너비를 실제 인스턴스 문자열의 너비에 따름 (UI: 번호 너비를 자릿수에 맞춤) |
| bit 3     | 자동 내어 쓰기                                                       |
| bit 4     | 본문과의 거리 종류. 0 글자 크기에 대한 상대 비율(%), 1 **HWPUNIT**  |
| **bit 5~9** | **번호 형식(표 41)**\*\*                                           |

\*\* bit 10 이상을 켜면 한글은 번호를 1, 2, 3으로 그린다. 의미는 모른다. 한글이 저장하는 값은 bit 5~9 안에 들어간다.

**[표 41] 문단 번호 형식**: 0 1,2,3 / 1 ①②③ / 2 I,II,III / 3 i,ii,iii / 4 A,B,C / 5 a,b,c / 6 Ⓐ,Ⓑ,Ⓒ / 7 ⓐ,ⓑ,ⓒ / 8 가,나,다 / 9 ㉮,㉯,㉰ / 10 ㄱ,ㄴ,ㄷ / 11 ㉠,㉡,㉢ / 12 일,이,삼 / 13 一,二,三 / 14 ㊀,㊁,㊂ / **15 갑,을,병 / 16 甲,乙,丙**.
