## 코드

- [x] **COLORREF 최상위 바이트 손실** (2026-11-02): 배경색 `FF FF FF FF`를 다시 쓰면 `FF FF FF 00`이 된다. `reader.color()`가 최상위 바이트를 버린다. `0xFFFFFFFF`가 "색 없음"을 뜻하는지도 함께 확인. `border-fill.test.ts`에 `it.fails`로 표시해 둠. → 읽기·쓰기 모두 네 바이트 보존. 셀 배경에서 `FF FF FF FF`는 색 없음, `FF FF FF 00`은 흰색으로 확인. 최상위 바이트의 의미는 미확인(`experiments/colorref-high-byte`).
- [ ] **`ImageFillMode.None` 이름**: 한글 표기는 "원래 크기에 비례하여". 동작을 드러내는 이름으로 바꿀지 결정.

- [ ] **DocInfo 미파싱 레코드 네 개**: 지금은 `preserved.docInfoTail`에 원본 그대로 보존만 한다. 쓰는 쪽이 생길 때 파싱한다.
  - 호환 문서(0x01E, 대상 프로그램 UINT32)·레이아웃 호환성(0x01F, UINT32 × 5): 조판 시작 시. 줄 나눔·배치 규칙을 바꾸는 플래그라 쪽수 측정에 영향. 모르는 비트는 `unknownBits`로 보존.
  - 배포용 문서 데이터(0x01C, 256바이트 시드): 배포용 문서(ViewText 복호화) 지원 시. 지금은 배포용 문서를 거부한다.
  - 문서 임의의 데이터(0x01B, 파라미터 셋): 쓰는 곳이 생기면.
  - tail을 맨 뒤에 몰아 쓰므로 이 레코드들이 늘 Style 뒤에 온다는 가정이 깔려 있다. 실제 파일로 순서 미확인.
- [ ] **편집 후 줄 정보 갱신**: 지금은 PARA_LINE_SEG를 읽은 그대로 다시 써서, 텍스트를 고쳐도 옛 줄 정보가 남는다. 한 문단의 줄 수가 바뀌면 뒤 문단의 `y`와 쪽 첫 줄 플래그도 바뀌므로 고친 문단부터 구역 끝까지 다시 배치해야 한다.
  - 바뀐 문단 찾기: 편집 API 미들웨어는 모델을 직접 고치면 우회된다. 읽을 때 문단마다 텍스트·글자 모양·문단 모양 지문을 남기고, 쓸 때 비교해 바뀐 문단을 찾는다.
  - 계산 시점: 편집마다가 아니라 직렬화할 때 한 번.
  - 단계: (1) 바뀐 문단부터 기본값으로 무효화 → (2) 한글 실측("줄 정보가 틀리거나 없을 때 한글의 동작") 결과로 충분한지 판단 → (3) 필요하면 조판 엔진(렌더러와 공유)으로 정확히 계산.

- [x] **unknown 컨트롤의 자식 레코드 손실** (2026-11-24): `readControl`이 모르는 ctrlId를 `unknown`으로 만들면 CTRL_HEADER 페이로드만 보존하고 자식 레코드는 버렸다. 그리기 개체·글상자(`gso `), 수식(`eqed`), 한글이 저장한 그림(SHAPE_COMPONENT_PICTURE가 손자라 `readDrawingObject`가 알아보지 못함)이 해당했다. → `UnknownControl.childRecords`에 하위 레코드를 CTRL_HEADER 기준 깊이와 함께 보존해 그대로 다시 쓴다. `gso `는 CTRL_HEADER를 `placement`로, 캡션을 `placement.caption`으로 쓰고(캡션 레코드는 `childRecords`에서 뺀다) `raw`를 두지 않는다. `unknown-control.test.ts`가 저장소 HWP 파일의 `gso `·`eqed` 하위 트리 전체를 바이트 비교한다. gso가 든 파일 38개 중 BodyText 구역 레코드가 원본과 같은 파일이 0개에서 36개가 됐다. 나머지 2개는 대화상자가 만들지 않는 값을 넣은 실험 파일로, 표와 같은 규칙에 따라 캡션 없는 bit 29를 끄고 세로 기준 3을 2(문단)로 쓴다(`experiments/object-props-out-of-dialog`). 글상자 문단과 그 안의 개체는 모델로 읽지 않으므로 편집 API로 고칠 수 없다.
- [ ] **그림·그리기 개체 캡션**: 표 캡션은 2026-11-19에 읽고 쓰도록 고쳤다(bit 29는 캡션을 쓸 때만 켠다). 2026-11-20부터 `gso `도 SHAPE_COMPONENT 앞의 캡션 LIST_HEADER와 문단을 `placement.caption`으로 읽는다(`readLeadingCaption`, `experiments/object-common-props/rect-caption-bottom.hwp`). `writePicture`도 캡션을 SHAPE_COMPONENT 앞에 쓰고 bit 29를 켠다(한글에서 미확인). 2026-11-24부터 그리기 개체(unknown `gso `)도 캡션과 bit 29를 모델로 쓰고 나머지 자식 레코드를 보존한다(한글에서 캡션을 고쳐 저장해 보지는 않았다). 남은 것: 한글이 저장한 그림은 SHAPE_COMPONENT_PICTURE가 손자라 `readDrawingObject`가 그림으로 알아보지 못한다. 빌더로 만든 그림 문서는 캡션이 없어도 한글이 "파일을 읽거나 저장하는데 오류가 있습니다"로 열지 못했다(BMP, 수정 전 코드도 같음). 빌더의 왼쪽·오른쪽 캡션은 캡션 폭을 본문 폭으로 잡아 오른쪽 여백 밖으로 나간다.
- [x] **LIST_HEADER 문단 수와 속성 위치** (2026-11-19): 문단 리스트 헤더는 문단 수 INT32 + 속성 UINT32(오프셋 4)다(정정 83, `experiments/list-header-para-count`). 표 셀(`readTableCell`, `writeTableCell`)은 문단 수를 UINT16으로, 속성을 오프셋 2부터 읽고 쓴다. 그래서 문단 65,536개를 넘는 셀은 문단이 잘리고(70,001 → 4,465), 셀 세로 정렬은 늘 위로 읽히며, 쓸 때는 bit 5가 늘 켜져 한글에서 가운데로 보일 것으로 추정한다(미확인). 각주·머리말 등 다른 LIST_HEADER 읽기도 같은지 확인한다. 표 캡션은 이미 이 구조로 읽고 쓴다. → `readListHeader`/`writeListHeader` 공용 함수로 셀·캡션·문단 리스트가 문단 수 UINT32, 속성 오프셋 4로 읽고 쓴다. 문단은 레코드 구조로 나눈다. 셀 세로 정렬은 한글에서 확인했다(`experiments/cell-vertical-align`). 셀 속성의 나머지 비트는 `listUnknownBits`로 보존한다.
- [x] **셀 LIST_HEADER 속성 비트** (2026-11-20): 글자 방향(bit 0~2), 줄바꿈(bit 3~4), 셀 속성 bit 16~20을 `TableCell` 필드로 읽고 쓴다(정정 85, E33, `experiments/list-header-properties`). 쓰이지 않던 `shrinkToFit`, `noWrap` 필드는 `lineWrap`(`ListLineWrap`)으로 바꿨다. bit 0~6은 `readListHeader`가 모든 LIST_HEADER에 공통으로 해석한다(`ListProperties`).
- [ ] **LIST_HEADER 속성 bit 24, 26의 뜻**: 한글 문서 셀에 흔하지만 HWPX에 대응 속성이 없다. 마지막 셀에 셀 보호를 켜면 bit 26이 켜지는 것만 봤다. 지금은 `listUnknownBits`로 보존한다.
- [x] **셀이 아닌 LIST_HEADER의 속성 해석** (2026-11-23): 문단 리스트를 가진 모델(셀, 캡션, 머리말·꼬리말, 각주·미주, 숨은 설명, 바탕쪽, 메모)이 모두 `ParagraphList`를 확장한다. `readListHeader`가 bit 0~6을 필드로, 나머지 비트를 `listUnknownBits`로 읽는다. 캡션은 2026-11-20에 먼저 고쳤다(정정 86, E34, `experiments/caption-list-properties`). 셀·캡션이 아닌 리스트는 헤더 8바이트 뒤를 해석하지 않고 `listTrailing`으로 보존한다(전에는 속성까지 `listHeaderRest`로 통째 보존했다). 저장소 HWP 파일의 쓰기 결과는 바뀌지 않았다. 꼬리말 LIST_HEADER의 세로 정렬은 아래(2), 바탕쪽·메모는 위(0)였다.
- [ ] **셀·캡션이 아닌 LIST_HEADER의 뒤 바이트와 새 리스트 형식**: 머리말·꼬리말·바탕쪽 LIST_HEADER는 34B, 메모는 16B인데 코덱은 헤더 8바이트 뒤(`listTrailing`)를 해석하지 않는다. 명세는 머리말·꼬리말(표 140)과 바탕쪽(표 137)에 텍스트 영역 폭·높이와 참조 바이트 2개(10B)를 적었지만 위치를 확인하지 않았다(정정 68). 새로 만든 리스트는 헤더 8바이트만 쓴다. 한글이 새 머리말·바탕쪽·메모에 쓰는 바이트와 bit 0~6 기본값, 그리고 이 리스트들의 글자 방향·줄바꿈 비트 배치를 한글로 확인해야 한다.
- [x] **표 속성(표 76)의 명세에 없는 비트 손실** (2026-11-24): `readTable`은 bit 0~1(쪽 경계에서 나눔)과 bit 2(제목 줄 자동 반복)만 읽고, `writeTable`은 이 둘로 속성을 새로 만들어 나머지 비트를 버린다(`06000004` → `06000000`). 저장소 HWP 파일의 TABLE 464개에서 명세에 없는 bit 3(167개), 24(27개), 25(148개), 26(322개)이 켜져 있었다. 값은 `0x04000006`, `0x0600000c`, `0x00000006`, `0x01000006`, `0x0400000e` 순으로 흔하다. 2026-11-24 한글로 확인했다(정정 88, E36, `experiments/table-property-bits`). bit 0~1 값 2는 "나눔"으로 모델 `PageBreakInTable.Split`과 맞다. bit 3은 HWPX `noAdjust`다. bit 24는 한글이 다시 저장할 때 지우고, bit 25, 26은 한글이 보존하지만 뜻을 모른다. → bit 3을 `TableControl.noAdjust`로, bit 0~3 밖의 비트를 `TableControl.unknownBits`로 읽고 쓴다. `table.test.ts`가 저장소 HWP 파일의 TABLE 레코드 전체를 바이트 비교한다. bit 3, 25, 26의 뜻은 아직 모른다.
- [x] **셀 LIST_HEADER 34B 뒤 바이트 보존** (2026-11-20): 표 80 뒤 12~13B를 `TableCell.trailing`으로 보존하고, 병합 수를 읽은 그대로 둔다(0도). 저장소 HWP 파일의 LIST_HEADER 전체 바이트 왕복 테스트로 확인한다. 새 셀은 한글처럼 셀 폭과 0 9바이트를 쓴다.


## 한글 실측

- [ ] **기준을 문단으로 바꿀 때 한글의 정렬 처리**: 가로 안쪽·바깥쪽, 세로 가운데·아래로 둔 개체의 기준을 문단으로 바꾸면 한글 대화상자가 정렬을 무엇으로 바꾸는지 확인한다(왼쪽·위로 초기화되는지 등).
- [ ] **개체 요소 속성(표 83) bit 29와 다각형·곡선 끝 4바이트의 뜻**: bit 19(`rotateimage`), 24(글상자), 25(회전한 그림), 26(그림), 회전·대칭, 변환 행렬 관계는 정정 101, E50~E52에서 확인했다. bit 29(그림이면 켜짐, HWPX 대응 없음)와 다각형·곡선 끝 4바이트는 바꿔도 그림이 같아 뜻을 모른다. `unknownBits`, `polygonTrailing`, `curveTrailing`으로 보존한다. 묶음 안 개체의 scaleRotations 둘 이상도 아직 보지 못했다.
- [ ] **COLORREF 최상위 바이트의 정체**: 왜 존재하고 무엇을 뜻하는지 파악한다. 지금까지 확인한 것은 셀 배경의 `FF FF FF FF`(색 없음)와 `FF FF FF 00`(흰색)뿐이다. 모델에는 `Rgb.unknown`으로 보존한다.
- [ ] **이미지 효과 값**: 회색조·흑백 등으로 바꿔 저장했을 때 효과 바이트가 바뀌는지 확인. 지금까지 0만 봤다.
- [ ] **이미지 명암·밝기 음수**: −20 같은 음수로 저장해 INT8로 읽히는지(`ec`) 확인.
- [ ] **대각선 kind 0과 2**: 대각선 선 종류를 "없음", 파선 등으로 바꿔 LineStyle 대응 확인. 지금까지 1(실선), 3(점선)만 확인했다.
- [x] **복수 채우기 종류의 우선순위** (2026-11-24): 한글은 하나만 저장하지만, 두 비트가 켜진 파일(단색+그러데이션, 종류 5)도 오류 없이 열린다. 어떤 종류를 우선해 그리는지 확인. 지금까지는 종류 5에서 속성 창이 그러데이션을 보였을 뿐이고, 그 시험 파일은 번짐 정도가 0이라 실제로 무엇을 그리는지는 몰랐다. 조합 3(단색+이미지), 5, 6(그러데이션+이미지), 7(전부)을 비교한다. → Windows 한글 2024에서 3·6·7은 그림, 5는 그러데이션을 그렸다. 한글은 여러 블록을 보존하고 대화상자로 색 + 그림, 그러데이션 + 그림을 만든다. 모델을 `Fill { color?, gradient?, image? }`로 일반화했다(정정 92, E40, `experiments/fill-multi-kind-priority/windows-2024`).
- [ ] **그러데이션 색 위치 배열** (Windows 필요): 색 수 > 2일 때의 위치 INT32 × num 배치. macOS 한글은 3색 이상을 설정할 수 없다.
- [ ] **줄 간격 두 칸 읽기 규칙이 바뀌는 버전**: 5.0.2.5 파일은 새 칸 종류가 0이면 옛 칸을, 5.1.1.0 파일은 늘 새 칸을 읽는다(정오표 E20). 그 사이 버전(54B 문단 모양을 쓰는 5.0.4~5.0.5 등)은 확인하지 않아 코덱은 5.1.1.0 미만을 5.0.2.5처럼 읽는다. 그 버전의 파일에서 두 칸을 다르게 넣어 문단 모양 창으로 확인한다. 말뭉치의 54B 레코드 569개는 두 칸이 같아 지금은 결과에 영향이 없다.
- [ ] **스타일 언어 아이디의 영문 값**: 영문 환경(영문 한글 또는 영문 Windows)에서 저장한 파일의 스타일 언어 아이디를 확인한다. LCID라면 en-US는 1033(`0x0409`)이 예상된다. 지금까지는 실제 파일 99개의 스타일 1,995개가 모두 1042(ko-KR)였다(정오표 정정 48).
- [ ] **구역 첫 문단에서 `cold`가 `secd`보다 먼저 오는 파일**: `fixtures/kogl_hwp/2020년도 연맹 사무처장 공개채용 공고 제출양식.hwp`(5.0.2.5)와 이 파일에서 만든 `scratch/parashape-46-with-58/*` 15개는 구역 첫 문단이 `cold → secd → tbl ` 순서다. 쓰기 코드는 늘 `secd → cold`로 써서 PARA_TEXT와 CTRL_HEADER 순서가 바뀐다. 저장소의 다른 파일은 모두 `secd`가 먼저이고, 다른 5.0.2.5 파일도 그래서 버전만의 차이는 아니다. 한글에서 이 순서를 재현할 수 있는지(어떤 조작이나 버전에서 생기는지), 바뀐 순서로 써도 한글이 똑같이 여는지 확인한다. 재현되면 `Section`에 순서를 보존하고, 아니면 정규화로 둔다. 지금은 `para-text-roundtrip.test.ts`가 이 두 컨트롤의 순서만 무시하고 비교한다.
- [ ] **줄 정보(PARA_LINE_SEG)가 틀리거나 없을 때 한글의 동작**: 문단 텍스트를 고친 뒤 옛 줄 정보를 그대로 둔 파일, 기본값(`defaultLineSegment`)으로 바꾼 파일, 레코드를 뺀 파일을 한글에서 열어 다시 배치하는지, 겹치거나 깨져 보이는지 확인한다. 결과에 따라 아래 "편집 후 줄 정보 갱신"의 범위를 정한다.
