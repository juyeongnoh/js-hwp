## 코드

- [x] **COLORREF 최상위 바이트 손실** (2026-11-02): 배경색 `FF FF FF FF`를 다시 쓰면 `FF FF FF 00`이 된다. `reader.color()`가 최상위 바이트를 버린다. `0xFFFFFFFF`가 "색 없음"을 뜻하는지도 함께 확인. `border-fill.test.ts`에 `it.fails`로 표시해 둠. → 읽기·쓰기 모두 네 바이트 보존. 셀 배경에서 `FF FF FF FF`는 색 없음, `FF FF FF 00`은 흰색으로 확인. 최상위 바이트의 의미는 미확인(`experiments/colorref-high-byte`).
- [ ] **`ImageFillMode.None` 이름**: 한글 표기는 "원래 크기에 비례하여". 동작을 드러내는 이름으로 바꿀지 결정.
- [x] **`borderFillId` 1 어긋남** (2026-11-15): 파일은 1부터 세고 모델은 0부터 센다. 글자 모양·문단 모양은 읽기·쓰기 모두 값을 그대로 둬서 모델 값이 1 크다. 표는 그대로 읽고 `+ 1`로 써서 저장할 때마다 1씩 커진다(`base-orange.hwp`에서 3 → 4 → 5 재현). 파일의 0은 `undefined`로 구분할지 함께 결정. → 문단 모양 번호·글머리표·테두리, 글자 모양·표·셀 테두리 모두 1을 빼서 읽고 1을 더해 쓴다. 파일의 0은 `undefined`.


## 한글 실측

- [ ] **COLORREF 최상위 바이트의 정체**: 왜 존재하고 무엇을 뜻하는지 파악한다. 지금까지 확인한 것은 셀 배경의 `FF FF FF FF`(색 없음)와 `FF FF FF 00`(흰색)뿐이다. 모델에는 `Rgb.unknown`으로 보존한다.
- [ ] **이미지 효과 값**: 회색조·흑백 등으로 바꿔 저장했을 때 효과 바이트가 바뀌는지 확인. 지금까지 0만 봤다.
- [ ] **이미지 명암·밝기 음수**: −20 같은 음수로 저장해 INT8로 읽히는지(`ec`) 확인.
- [ ] **대각선 kind 0과 2**: 대각선 선 종류를 "없음", 파선 등으로 바꿔 LineStyle 대응 확인. 지금까지 1(실선), 3(점선)만 확인했다.
- [ ] **복수 채우기 종류의 우선순위**: 한글은 하나만 저장하지만, 두 비트가 켜진 파일(단색+그러데이션, 종류 5)도 오류 없이 열린다. 어떤 종류를 우선해 그리는지 확인. 지금까지는 종류 5에서 속성 창이 그러데이션을 보였을 뿐이고, 그 시험 파일은 번짐 정도가 0이라 실제로 무엇을 그리는지는 몰랐다. 조합 3(단색+이미지), 5, 6(그러데이션+이미지), 7(전부)을 비교한다.
- [ ] **그러데이션 색 위치 배열** (Windows 필요): 색 수 > 2일 때의 위치 INT32 × num 배치. macOS 한글은 3색 이상을 설정할 수 없다.
- [ ] **줄 간격 두 칸 읽기 규칙이 바뀌는 버전**: 5.0.2.5 파일은 새 칸 종류가 0이면 옛 칸을, 5.1.1.0 파일은 늘 새 칸을 읽는다(정오표 E20). 그 사이 버전(54B 문단 모양을 쓰는 5.0.4~5.0.5 등)은 확인하지 않아 코덱은 5.1.1.0 미만을 5.0.2.5처럼 읽는다. 그 버전의 파일에서 두 칸을 다르게 넣어 문단 모양 창으로 확인한다. 말뭉치의 54B 레코드 569개는 두 칸이 같아 지금은 결과에 영향이 없다.
- [ ] **스타일 언어 아이디의 영문 값**: 영문 환경(영문 한글 또는 영문 Windows)에서 저장한 파일의 스타일 언어 아이디를 확인한다. LCID라면 en-US는 1033(`0x0409`)이 예상된다. 지금까지는 실제 파일 99개의 스타일 1,995개가 모두 1042(ko-KR)였다(정오표 정정 48).
- [ ] **정오표의 Windows 후속 항목** (Windows 필요): `hwp-5.0-errata.md`의 "Windows에서 후속 확인할 사항" 참고.
